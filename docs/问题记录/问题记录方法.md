# 问题记录方法

> 用途：规定 `docs/问题记录/问题记录.md` 的写入规范，并给出可直接复制的提示词。此后任何新问题（生产故障、联调缺陷、测试发现）都按本文件执行，保证条目格式统一、证据可复核。

## 一、写入规范

### 1. 文件与编号

- 目标文件：`docs/问题记录/问题记录.md`（与本文件同目录）。
- 新增条目**追加在文件末尾**，标题格式：`# 问题N：<一句话概括现象或主题>`。
- 编号规则：若文件末尾存在占位条目（`# 问题N：xxx`），直接替换该占位；否则取现有最大编号 +1。
- 不改动、不重排历史条目；同一问题后续有进展，回填到原条目内，不新建编号。
- 内容来源：只写对话/排查中已确认的事实；信息缺失时向提问者确认，不得编造，确需留白的写「待补」。

### 2. 条目结构（信息头 + 固定四段）

```markdown
# 问题N：<一句话概括>

- 发现时间：<绝对日期，注明时区；DB 时间为 UTC 时需说明>
- 环境：<入口/主机 + 部署版本（部署时间或提交号）>
- 状态：<已定位待修复 / 修复中 / 已修复待验证 / 已关闭 / 无法复现>

表现：

原因：

解决方案：

实际处理方案：
```

### 3. 各字段写作要求

| 字段 | 要求 |
|---|---|
| 发现时间 | 绝对日期 + 时区（禁止「今天/昨天/上周」）；DB 查询结果如为 UTC 需换算说明 |
| 环境 | 具体入口与主机；部署版本用最近一次部署时间或提交号 |
| 表现 | 用户/访客看到的**原文照抄**；附影响面（谁受影响）、频率（偶发/必现）、耗时等可量化指标 |
| 原因 | 先给直接触发点，再给机制；引用代码必须带 `文件:行号`；区分「已确认」与「推断」，推断必须显式标注 |
| 证据 | 日志/SQL/截图**原文照抄**，并写明采集命令，便于他人复核 |
| 解决方案 | 按优先级编号，每条标注类型：【治本】【止血】【权宜】【可观测性】；写清代价与副作用 |
| 实际处理方案 | 修复完成后回填（改了什么、提交号、验证结果）；未修复写「（待处理）」 |

### 4. 证据采集命令（生产只读模板）

```bash
# 应用日志（harness 容器），关键词按需替换
ssh jj@192.168.31.66 'sudo -n docker logs --since 48h lingnan-production-harness-1 2>&1 | grep -F 关键词 | tail -40'

# 带时间戳排查（用于把日志事件对应到具体请求）
ssh jj@192.168.31.66 'sudo -n docker logs -t --since 48h lingnan-production-harness-1 2>&1 | grep -E "关键词1|关键词2" | tail -30'

# 问答记录（只读 SELECT，psql 直接读取容器内环境变量，无需密码）
ssh jj@192.168.31.66 'sudo -n docker exec lingnan-production-postgres-1 sh -c "psql -U \$POSTGRES_USER -d \$POSTGRES_DB -c \"SELECT \\\"createdAt\\\", status, \\\"elapsedMs\\\", left(question,40) FROM \\\"ConsultationQaRecord\\\" ORDER BY \\\"createdAt\\\" DESC LIMIT 25;\""'
```

校外咨询常用日志关键词：`模型生成失败`（上游调用失败降级）、`答案校验拦截`（守门员拦截原因）、`[consultation] Reply failed`（LibreChat 侧异常）。

### 5. 写法：业务语言打头，技术锚点紧随（硬性要求）

记录要同时满足两个目标：**没参与排查的人能读懂**，**日后要定位/复现的人能照着找到代码**。**两头都要有**——只写代码看不懂，只写业务找不到地方。

**先讲业务，再给机制，在同一段里完成。**
每段先用一句人话说清「这在业务上是什么、谁受影响」，紧接着给出对应的机制、字段或代码位置。不要把它们拆到两个地方，也不要只剩一头。

**必须保留的技术锚点**（这些正是理解逻辑的关键，不要因为"太技术"而删掉）：

| 保留什么 | 为什么 | 怎么写 |
|---|---|---|
| 关键函数 / 文件位置 | 定位与复现的入口 | `文件:行号` + 函数名，紧跟在解释它的那句话后面 |
| 关键字段名、表名、常量 | 它们往往就是「为什么这样设计」的答案（如 `reasoning_content`、`@@unique([provider, principalId])`、`enable_thinking`） | 原样写出，**首次出现时用一句话解释它的含义** |
| 设计逻辑与取舍 | 避免后人重复踩同一个坑 | 写清为什么这样设计、为什么不能那样做 |

**术语首次出现必须给一句解释。**
例：`@@unique([provider, principalId])`（含义：同一个人在同一种登录方式下，只能有一条身份记录）。

**必须配真实例子或比方。** 用本次事件的**具体现象**（报错原文、访客看到的那句话、界面上的表现），或一个贴切的类比。

**合格标准（两条都要满足）**：
1. 没参与排查的同事读完能说出「哦，原来是这么回事」；
2. 他能照着记录**找到对应的代码、把问题复现出来**。

**反面 vs 正面（取自本仓库真实问题）**

❌ 反面一——只摆机制与行号，读者不知道在说什么：

> 原因：`ensureIdentityTransaction` 的 `create` 分支触发 `@@unique([provider, principalId])`，P2002 在 catch 内重试后仍冒泡为 500。

❌ 反面二——全是大白话，丢掉了关键机制与字段，读者无法定位代码：

> 原因：一个人可以有两种登录方式，删掉记录后重建，程序误以为冲突就报错了。

✅ 正面——业务语言打头，关键机制 / 字段 / 代码位置紧随其后：

> 原因：系统里一个「人」可以同时用**校内账号**和**统一身份认证**两种方式登录，这两条身份记录绑在同一个人身上。
> 具体是怎么绑的：表 `ExternalIdentity` 用 `(provider, subjectId)` 唯一标识一个外部身份（provider 是登录方式，subjectId 是对方系统里的编号），同时用 `@@unique([provider, principalId])` 保证「一个人在同一种登录方式下只有一条记录」。
> 出问题的动作发生在 `ensureIdentityTransaction`（`bridge-service.controller.ts:589`）：它**只按 `(provider, subjectId)` 查，查不到就新建**。当本地用户被删掉重建、系统内部编号（Mongo `_id`）变了，新记录想再挂到同一个人身上，就撞上了第二条约束。
> **其实数据并没有冲突，只是同一个人的记录换了一代**——正确做法是把旧记录改指到新编号，而不是新建。
> 表现在用户侧：**该账号从此再也登不进来**，屏幕上只显示「账号服务暂时不可用」。

## 二、提示词（复制给 Claude 使用）

> **怎么用**：在对话里跟 AI 把一个问题排查清楚后，发一句话就行。现象、报错原文、结论、代码位置都还在当前对话里，AI 会自己提取，你不用整理粘贴。
> **什么时候会自己发生**：常驻规则已写进项目根目录 `CLAUDE.md` 与 `AGENTS.md`，新会话自动生效，结论稳定后自动写入。本节提示词用于手动补记、或调整已写好的条目。
> **最重要的要求**：**业务语言打头，技术锚点紧随**。先说业务（谁受影响、用户看到什么），紧接着给出关键函数 / 字段 / 配置项与代码位置，并**必须配一个真实例子**。**只堆代码看不懂、或只剩大白话找不到地方，都不合格。** 详见「一、写入规范」第 5 条。

**标准写法**

```text
把本次对话中已排查清楚的问题，按 docs/问题记录/问题记录方法.md 的规范写入 docs/问题记录/问题记录.md。
注意写法：业务语言打头，技术锚点紧随——先说清这是什么问题、谁受影响、用户看到什么，紧接着给出关键函数/字段/配置项与代码位置，并配一个本次的真实例子（报错原文或现象）。关键字段名、表名、常量、设计取舍都要保留，首次出现时用一句话解释；不要写成纯术语堆砌，也不要写成丢掉机制的大白话。
```

**变体**

- 问题已修复：「把本次对话解决的问题按规范写入问题记录（业务语言打头 + 保留关键代码/字段/设计逻辑 + 配真实例子），并在「实际处理方案」回填改了什么、验证结果。」
- 仍在解决中：「把本次对话正在解决的问题按规范写入问题记录，状态标「修复中」，「实际处理方案」写待处理。」
- 补充进展：「把问题N的后续进展按规范回填到原条目，不要新建编号。」
- **觉得现有条目看不懂**：「把问题N改写成：业务语言打头，但保留关键函数/字段/约束名与设计取舍（首次出现加一句解释），并补一个真实例子。」
- **觉得现有条目太空、找不到代码**：「把问题N补上关键函数、字段名与代码位置，同时保持业务语言打头。」
- **只记某一个点**：「把本次对话里关于 <主题> 的排查按规范写入问题记录。」

执行细则（编号、结构、字段要求、取证命令）统一以「一、写入规范」为准。

## 三、范例

- `问题1：生产偶发「咨询助手暂时无法组织回答」——历年录取分数线提问上游模型超时`：完整示范了信息头、四段式写法、证据表（日志 + SQL 结果 + 代码行号）与分级解决方案。
