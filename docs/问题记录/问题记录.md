# 问题1：技师学院咨询页主题蓝太浅，白字与序号「看不清」

- 发现时间：2026-10-30（UTC+8），用户在同一轮改造中报告
- 环境：本地开发环境 `http://127.0.0.1:5300/chat-jishi.html`，容器 `vocational-langbot-core`（镜像内挂载 `data/docker -> /app/data`），分支 `my/custom`，LangBot 4.11.2
- 状态：已修复待验证（本地 5300 已实测通过，未上生产）

表现：

用户原话：**「主题颜色和 logo 的颜色不是那么搭配，蓝色太浅配黑色文字的时候看不清晰，序号显示也不清晰」**。

打开页面即可复现，必现。访客能看到三处问题：顶部标题栏是浅蓝底 + 深灰黑字，读起来发闷；被选中的角色标签（如「校内教师」）同样是浅蓝底配黑字；问题列表左侧的 `01`、`02` 序号在浅灰卡片上几乎糊成一片。影响的是技师学院这一个入口的全部访客，不影响 `chat.html`（砖红 `#72030C`，本身够深）。

原因：

根因是**主色亮度太高，而页面又同时把它当作「底」和「字」两种角色用**。`chat-jishi.html` 当时只传 `"accent": "#20bfff"`（院徽主蓝的浅化版），没有任何显式的前景色。widget 于是分两路各自动手：

1. **当作底**：`buildThemeCSS()`（`src/langbot/templates/embed/widget.js:382`）把 accent 铺到 `.lb-header`、选中态 `.lb-role-tab.lb-role-active`（`:408`）、发送按钮上，文字色用 `p.onAccent`。
2. **当作字**：`buildConsultCSS()` 里 `.lb-q-index { color: p.accent }`（`:416`）直接拿 accent 当序号文字色，背景是 `.lb-role-question` 的 `#f9fafb`。

`p.onAccent` 不是写死的，而是由 `pickOnAccent()`（`:342`）按 WCAG 相对亮度公式在纯白 `#ffffff` 和近黑 `#111827` 之间挑对比度更高的一个。`#20bfff` 的相对亮度偏高，**白字对比度只有 2.11:1、黑字有 8.41:1**，函数自然选了黑字——所以「浅蓝配黑字」不是配错了，而是自动选色的必然结果。而序号方向相反：浅蓝字压在接近白的卡片上，对比度 2.02:1，比正文还低，于是发虚。

两个方向都低于 WCAG AA 正文要求的 4.5:1，这就是「看不清」的量化解释。

解决方案：

1. 【治本】把主色换成**更深的同色系蓝**：院徽主蓝是 `rgb(19,121,181)`（`#1379B5`），再压暗一档取 `#0f6fa8`。加深后白字 5.44:1、序号对 `#f9fafb` 5.21:1，`pickOnAccent()` 自动改选白字，hover 派生值（`mixHex` 压暗 12% → `#0d6294`）也有 6.58:1。**只改一个色值即可，不需要手写 hover / border / 前景色**——派生链会跟着一起变深。
2. 【可观测性】在 `web/tests/e2e/chat-page-consult.spec.ts:153` 用 `await expect.poll(() => headerBackground(page)).toBe('rgb(15, 111, 168)')` 锁死这个色值，防止后续有人改回浅色。
3. 【权宜】不推荐用 `accentHover` / `onAccent` 手工补救：主色仍浅时，序号这类「文字用 accent」的位置无法通过前景色修正，只能改主色本身。

实际处理方案：

- `web/public/chat-jishi.html:27` 的 `"accent"` 由 `#20bfff` 改为 `#0f6fa8`，并在文件头 HTML 注释里写清「院徽蓝 `rgb(19,121,181)`，加深到 `#0f6fa8` 以保证至少 5:1」。
- `docker cp` 同步到容器 `/app/web/dist/chat-jishi.html`（静态文件带 `no-store`，刷新即生效，无需重启）。
- 真实环境用 Playwright 穿透 Shadow DOM 复核：header 背景 `rgb(15, 111, 168)`、文字 `rgb(255, 255, 255)`、选中 tab 同色白字、序号色 `rgb(15, 111, 168)`、首条序号文本 `01`。
- `pnpm test:e2e -- chat-page-consult` 5 个用例全部通过。

# 问题2：竖版院徽在方形 logo 槽位里被拉伸或裁切

- 发现时间：2026-10-30（UTC+8），同轮改造中自查发现（用户未报告）
- 环境：同问题1
- 状态：已修复待验证（本地 5300 已实测通过，未上生产）

表现：

换成竖版院徽后（职业技术学院 157×221、技师学院 76×98），同一个图片文件在页面上出现两种走样：

- 欢迎区与顶栏的 `<img>` 原本没有 `object-fit`，默认 `fill` 会**把竖图压成方块**，院徽的竖长比例被压扁；
- 气泡回退图（`widget.js:1713`）显式写了 `object-fit: cover`，会**按宽裁高**，竖图上下被切掉。

两者都不报错，只是「看起来怪」，容易被当成图片素材问题。

原因：

`.lb-header-logo`（`widget.js:438`，28×28）和 `.lb-welcome-logo`（`:508`，48×48；咨询页覆盖为 `:404` 的 56×56）是**固定方形槽位**，早期配的都是正方形图（`lingnan-bot.png`、`jishi-bot.png`），方图放进方框两种 `object-fit` 看不出差别，问题一直潜伏。

解决方案：

1. 【治本】三处 logo 槽位统一 `object-fit: contain`：图片按最长边完整缩进方框，多余方向留白，比例不变形也不裁切。
2. 【兼容性】方图在 `contain` 下渲染结果与 `cover` 一致，对既有页面零视觉差异；未传 `data-logo` 的普通嵌入完全不受影响。
3. 【保留】气泡回退图（`:1713`）是有意保持 `cover` 的：它是 40px 圆形头像位，`contain` 会露出白边，视觉上更像「缺图」。这一处未改。

实际处理方案：

- `widget.js:404`、`:438`、`:508` 三处补 `object-fit: contain;`，`docker cp` 同步到容器 `/app/src/langbot/templates/embed/widget.js`，并 `docker restart vocational-langbot-core`（模板在服务端拼装后下发，不是静态文件，必须重启）。
- 实测：`/chat-jishi.html` 顶栏 logo 自然尺寸读到 `[76, 98]`、`objectFit: "contain"`，院徽完整；`/chat.html` 读到 `[157, 221]`、`objectFit: "contain"`。

# 问题3：关闭扩展市场后「添加扩展」整页空白，自定义扩展也装不了

- 发现时间：2026-10-30（UTC+8），用户在生产环境报告
- 环境：生产 `http://192.168.31.66:5300/home/add-extension`，单机 Compose（`langbot` / `langbot_plugin_runtime` / `sqlbot` / `portal_gateway`），镜像 `langbot:4.11.2-897b580f371b`，LangBot 4.11.2，分支 `my/custom`
- 状态：已修复待人工确认（新镜像已上生产并验证资源包，浏览器端待用户点一次）

表现：

用户原话：**「显示不出来扩展市场吗我想添加自定义扩展也不行」**。

生产环境打开「添加扩展」页面是一片空白：既没有市场列表，也没有任何「手动添加」按钮。更关键的是，侧边栏里那些本该绕开市场的手动入口——上传本地 `.lbpkg`/`.zip`、添加 MCP 服务器、从 GitHub 安装、创建技能——点进去都是同一个空白页，等于**在关闭市场的部署里，所有自定义扩展都装不了**。这个部署是隔离网络环境（`PLUGIN__ENABLE_MARKETPLACE: "false"`），本来就只靠这些手动入口，所以影响是功能性的、100%（必现），不是偶发加载失败。

原因：

根因是**一个市场开关被当成了整页开关**。`web/src/app/home/add-extension/page.tsx` 的页面组件在渲染前直接做了整页 early return：

```tsx
if (!systemInfo.enable_marketplace) {
  return <div>…市场不可用…</div>;   // 已在修复中删除
}
```

而「手动添加」按钮并不是独立页面，它只是挂在市场页头部的一个 `extensionActions` 元素（文件上传 `<input>` + 弹层 `Popover`，见 `page.tsx` 中 `extensionActions` 定义），由 `<MarketPage headerActions={extensionActions} />` 渲染进市场列表。市场页不渲染 → `extensionActions` 也跟着消失。侧边栏那些入口则一律跳 `/home/add-extension?manual=1`（`HomeSidebar.tsx:1079`、`:1092`、`:1134`、`:1147` 等），参数只负责「打开后自动弹出弹层」，救不了空白页——只有「去市场」那一项受 `systemInfo.enable_marketplace` 控制（`HomeSidebar.tsx:1061`），其余手动入口是无条件的。

还有一层容易误判的现象：`systemInfo` 是模块级对象而不是 React state，初始值 `enable_marketplace: true`，要等 `/api/v1/system/info` 回来才被 `Object.assign` 改成 `false`。所以页面会先按「市场可用」渲染一帧再整页替换成空白，看起来就像「加载失败」。

解决方案：

1. 【治本】把「市场列表」当成页面中的一个区块，而不是整个页面。市场关闭时只替换这一块，手动入口照常渲染：
   - 外层 `AddExtensionPage()` 只做一件事：把 `Boolean(systemInfo?.enable_marketplace)` 传给 `AddExtensionContent`（`page.tsx:142`）；
   - `AddExtensionContent` 内部条件渲染（`page.tsx:1444`）：市场可用时渲染 `<MarketPage headerActions={extensionActions} />`；不可用时渲染一个空状态（标题 + 说明 + `{extensionActions}` 按钮组）。
   - `?manual=1` 的既有 `useEffect` 原样保留，所以侧边栏深链在两种状态下都能自动弹出菜单。
2. 【文案】空状态两句话走 i18n：`addExtension.marketplaceDisabledTitle` / `marketplaceDisabledHint`，8 个语言目录（`web/src/i18n/locales/*.ts`）同步补齐，避免在代码里硬编码中文/英文。
3. 【回归防线】`web/tests/e2e/fixtures/langbot-api.ts` 的 system info mock 增加 `marketplaceEnabled` 开关；新增 `web/tests/e2e/add-extension-manual-add.spec.ts` 两条用例：市场关闭时页面出现空状态且「Manual Add」弹层内容（拖拽上传区、GitHub、创建技能）可见；市场开启时不出现空状态。
4. 【不推荐】只改 `PLUGIN__ENABLE_MARKETPLACE` 打开市场：生产网络到 `https://space.langbot.app` 不通（实测 HTTP 000），打开后也只是空列表，且违背该部署的隔离加固意图。

实际处理方案：

- 代码：`page.tsx` 删除整页 early return，改为 `AddExtensionPage` + `AddExtensionContent({ marketplaceAvailable })` 两层；空状态使用 `Package` 图标 + 两行 i18n 文案 + `extensionActions`。八个 locale 文件各加两个键，`grep -c` 校验均为 2。
- 配置未动：`deploy/prod/docker-compose.yaml:90` 仍为 `PLUGIN__ENABLE_MARKETPLACE: "false"`，市场按设计保持关闭。
- 构建发布：本地 `docker buildx build --platform linux/amd64`（`Dockerfile` 第 7 行在镜像内 `npx vite build`）生成 `langbot:4.11.2-897b580f371b-addext`；`deploy/prod/ship-image.sh` 压缩传输并做 sha256 校验（577M）；生产 `/opt/langbot/.env` 先备份为 `.env.bak-20261030-addext` 再切 tag，`sudo docker compose up -d langbot` 后 `langbot Up (healthy)`。
- 验证：生产 `/api/v1/system/info` 返回 `"enable_marketplace": false`（符合预期）；首页加载的是新资源包 `assets/index-D3xC2NQ-.js`，其中 `marketplaceDisabledTitle` 出现 9 次；`pnpm lint` 0 error，`pnpm build` 通过，`pnpm exec playwright test tests/e2e/add-extension-manual-add.spec.ts --workers=1` 2 passed。
- 回滚：旧镜像 `langbot:4.11.2-897b580f371b` 仍在生产主机；把 `.env.bak-20261030-addext` 覆盖回去再 `up -d langbot` 即可。
- 排查提醒：并行跑多个 Playwright 任务会抢 4173 端口的 vite server，表现为长时间无输出、CPU 打满，实际不是用例失败；用 `--workers=1` 并在单进程下复跑即可。

延伸：可复用的判断方法（功能开关应只裁剪自己那块、不该整页 return）见[学习3：功能开关该「关到哪里」](../学习记录/学习记录.md#学习3功能开关该关到哪里关掉一块功能不等于关掉整个页面2026-10-30)。

# 问题4：导入 SqlBot 导出的 MCP 配置后一直「连接失败」

- 发现时间：2026-10-30（UTC+8），用户在生产环境报告
- 环境：生产 `http://192.168.31.66:5300`，`langbot` / `sqlbot` 同在 `langbot_network`，镜像 `langbot:4.11.2-897b580f371b-addext`、`sqlbot:1.10.3-383d972b7f24`
- 状态：已修复导出侧，待用户重新导入验证

表现：

用户在 SqlBot 的 API Key 页面导出某个数据源的 MCP 配置，粘贴到 LangBot「扩展 → MCP 服务器」导入，列表里这条 `sqlbot-datasource-2` 一直显示连接失败。容器日志反复出现：

```
MCP server sqlbot-datasource-2: Streamable HTTP transport failed (ConnectError: All connection attempts failed); not falling back to SSE
MCP session ... failed (attempt 1/2/3) ... ConnectError
Failed to start MCP server sqlbot-datasource-2(...): Connection failed, please check URL
```

表现上很像「MCP 客户端不支持 SqlBot」，实际从头到尾没有和 SqlBot 建立过一次 TCP 连接。

原因：

三层因素叠在一起，**第一层是真根因，后两层放大了误判**：

1. **导出的地址在生产拓扑里不存在**。SqlBot 的导出接口 `_mcp_public_url()`（`SQLBot/backend/apps/system/api/apikey.py:76`）在没有配置 `MCP_PUBLIC_URL` 时，用「浏览器请求的 Host + `MCP_PORT`」拼地址，于是导出了 `http://192.168.31.66:8001/mcp`。但生产的 Compose 里 SqlBot 的 8000/8001 **只声明不发布**（`docker ps` 显示 `8000-8001/tcp` 没有映射箭头），宿主机 IP:8001 没有任何进程监听。从 `langbot` 容器实测：`192.168.31.66:8001` 连接被拒，`sqlbot:8001` 正常。
2. **LangBot 对连接错误不回落 SSE**。`_init_remote_server()`（`src/langbot/pkg/provider/tools/loaders/mcp.py:511`）先试 Streamable HTTP，只有 400/404/405 这类「协议不兼容」响应才回落 SSE（`_should_fallback_to_sse()`，`:973`）。`ConnectError` 是网络不通，属于配置错误，按设计直接失败——否则会把「地址写错」伪装成「协议不兼容」。
3. **SqlBot 的 MCP 端点确实只讲 legacy SSE**：`POST /mcp` 返回 405，`GET /mcp`（带 Bearer）返回 `text/event-stream`。也就是说地址改对之后，LangBot 会先吃一个 405，再按设计回落 SSE 并连接成功。

解决方案：

1. 【治本】固定导出地址：给 SqlBot 注入 `MCP_PUBLIC_URL=http://sqlbot:8001/mcp`，导出时直接返回 Compose 服务名地址，不再依赖请求 Host。
2. 【兼容】保留 `MCP_PORT` 逻辑不动：`MCP_PUBLIC_URL` 为空时行为与原来一致，其他部署不受影响；需要给 Compose 之外的工具导出时，用 `.env` 覆盖成那个工具能访问的地址。
3. 【不推荐】把 8001 发布到宿主机来迁就导出地址：等于把带 Bearer token 的 MCP 端口暴露到校园网，与《自托管条款与安全评估》中「内部端口不要暴露」的约定冲突。

实际处理方案：

- `deploy/prod/docker-compose.yaml` 的 `sqlbot` 服务新增 `MCP_PUBLIC_URL: ${SQLBOT_MCP_PUBLIC_URL:-http://sqlbot:8001/mcp}`（约第 155 行，含注释说明为何不能用宿主机 IP）。
- 生产：`/opt/langbot/docker-compose.yaml` 备份为 `.bak-20261030-mcpurl` 后更新，`sudo docker compose --env-file .env up -d sqlbot` 重建，容器 45 秒后 `healthy`；容器内 `env` 与 `settings.MCP_PUBLIC_URL` 均读到新值。
- 验证：用库中现存的 Bearer token、把 host 换成 `sqlbot`，在 `langbot` 容器内跑完整 MCP 客户端（`sse_client` + `ClientSession`），`initialize` 成功，`list_tools` 返回 `['mcp_ask']`。
- 遗留：生产里那条 `sqlbot-datasource-2` 存的还是旧 URL，需要用户重新导出/导入，或把 URL 改为 `http://sqlbot:8001/mcp`；token 未变，可继续使用。
- 回滚：`sudo cp /opt/langbot/docker-compose.yaml.bak-20261030-mcpurl /opt/langbot/docker-compose.yaml && sudo docker compose --env-file .env up -d sqlbot`。
- 排查提醒：「连接失败」先分清是**没连上**还是**连上了但协议不对**：前者看 `ConnectError`/超时并核对地址可达性（容器内用服务名，不要用宿主机 IP），后者才会出现 400/404/405 与 SSE 回落日志。

# 问题5：Seedream 生图 MCP 接网关必报 403 `model_no_authorization`

- 发现时间：2026-10-30（UTC+8），同事在 Claude Code / Codex 配置时报告
- 环境：网关 `https://ai.ctaigw.cn/v1`，客户端为 Claude Code / Codex / WorkBuddy，包 `seedream-image-mcp==4.2.0`
- 状态：已修复（改用直通版 `4.2.0.post1` 并实测出图）

表现：

配好 MCP 后握手正常、6 个工具都在，但一调 `text_to_image` 就返回：

```
403 {"error":{"code":"model_no_authorization", ...}}
```

换成别名 `doubao-seedream-5.0-lite` 也一样。表面看像「Key 没授权这个模型」，实际是包和网关对模型名的理解不一致。

原因：

1. **网关只登记了别名**。`GET /v1/models` 里 Seedream 只有 `doubao-seedream-5.0-lite` / `Doubao-Seedream-5.0-lite` 两条，没有完整 Model ID `doubao-seedream-5-0-260128`，管理员也明确不支持加白。
2. **官方包强制把别名展开成完整 ID**。`seedream_mcp/_config_sources.py` 的 `normalize_model_selector()` 在启动构建配置时查 `MODEL_ALIASES`，`doubao-seedream-5.0-lite` 被改写为 `doubao-seedream-5-0-260128` 写回 `config.model_id`，请求体里的 `model` 就是网关不认的那个值。因此无论配置里填别名还是完整 ID，出去的请求都一样，403 必现。
3. 握手不受影响，因为 `initialize` / `tools/list` 不访问网关——这就是「工具都在、一出图就 403」的原因。

解决方案：

1. 【治本】给包加一个「模型名直通」开关：fork 上游（MIT），新增 `SEEDREAM_MODEL_PASSTHROUGH`，为 `true` 时 `normalize_model_selector` 只做 `strip()+lower()`、不查别名表，配置里的模型名原样进请求体；`false` 恢复官方语义。改动仅 `_config_sources.py` + `config.py`（一个字段 + 一个 picker 注册），版本号 `4.2.0.post1`。
2. 【分发】构建 wheel 发布到 GitHub Release，客户端用 `uvx --from <wheel URL> seedream-image-mcp` 启动，不依赖 PyPI 发版。
3. 【兜底】GitHub 不可达时用单文件 MCP 脚本（原样转发模型名），只有 `generate_image` 一个工具。

# 问题11：修复工具注入后 mcp_ask 返回 403「凭据校验失败」——SSO 独立工作区迁移后旧 MCP token 失效

- 发现时间：2026-11-03 08:49（Asia/Shanghai）
- 环境：同问题10；SQLBot 已于 2026-11-03 08:22 切换为 SSO 独立工作区镜像 `sqlbot:1.10.3-b2894486e674-sso-personal`
- 状态：修复中（新 token 已实测可用，待写回 LangBot 配置）

表现：

- `monitoring_tool_calls` 两条记录均为 `status=error`，`error_message='Error calling mcp_ask. Status code: 403. Response: "Could not validate credentials"'`。

原因：

- MCP 的鉴权凭据是一枚 **scoped JWT**（作用域令牌：把「哪个用户、哪个工作区、哪个数据源」写死在 token 里，SQLBot 每次调用按它校验权限）。LangBot 的 MCP 服务器 `sqlbot-datasource-1` 配置里那枚 token 是 2026-10-30 签发的，payload 为 `{"uid": 7521365110376370176, "oid": 1, "datasource_id": 2}`。
- SQLBot 在 11-03 08:22 做了 SSO 独立工作区迁移：`admin@vocational.local`（uid `7521365110376370176`）只属于**工作区 3**（`sys_user_ws` 只有 `(uid, 3)` 一行），数据源 `id=2` 也改归 `oid=3`；默认工作区 1 已无业务数据。旧 token 里的 `oid=1` 因此永远对不上。
- 校验点在 `apps/mcp/auth.py:152` 的 `_resolve_scoped_principal`：它要求 token 中的 `oid` 与 `core_datasource.oid` 一致，且非管理员用户必须属于该工作区；任何一项不满足都抛 `403 Could not validate credentials`。

证据：

```bash

#   fastapi.exceptions.HTTPException: 403: Could not validate credentials
# 数据库对照
#   sys_user_ws: (7521365110376370176, 3)
#   core_datasource: (id=2, oid=3, name=高职问数测试)
# 旧 token payload（解码不验签）: {"access_key":"lPYS-…","scope":"mcp","uid":7521365110376370176,"oid":1,"datasource_id":2}
```

解决方案：

1. 【治本】在 SQLBot 里用当前工作区重新导出 MCP 配置，再替换 LangBot 的 MCP 服务器 headers。SQLBot 的导出接口 `GET /api/v1/apikey/{id}/mcp-config?datasource_id=2`（`apps/system/api/apikey.py`）会按 **数据源实际所属工作区**重新签发 token，本质上就是把 `oid` 从 1 改成 3。
2. 【可观测性】SSO 工作区迁移、数据源迁移后，把「MCP 配置 token 重新导出」列为必做步骤；否则表现为工具能挂上、调用才 403，容易被误判为数据源故障。
3. 【权宜】短期也可用同一 API key 的 `secret_key` 手工签发 `oid=3` 的 token（与接口逻辑等价）。

实际处理方案：

- 已用 `sys_apikey.access_key='lPYS-9eQOBGj7SFraF-zqQ'` 的 `secret_key` 重新签发 JWT（`uid` 不变、`oid=3`、`datasource_id=2`），并直连 `POST /sqlbot/api/v1/mcp/mcp_ask` 实测：`HTTP 200`，返回真实 SQL 与数据 `{"major_name":"市场营销","graduates":130,"employed_count":128}`。

# 问题12：SqlBot 接口失效后落到 SqlBot 登录页，而不是 LangBot 统一退出

- 发现时间：2026-11-03（Asia/Shanghai）
- 环境：生产 `http://192.168.31.66:5300`，`portal_gateway` + LangBot + SqlBot 单机 Compose；入口 `/portal` →「SqlBot 智能问数」卡片；SQLBot 为带 LangBot SSO 补丁的定制镜像
- 状态：已修复待部署验证

表现：

- 从应用中心进入 SqlBot 后，只要某个接口返回 401（SqlBot token 过期或被服务端判定失效），页面会先短暂提示错误，随后刷新或跳转到 **SqlBot 自己的登录页 / 401 页**。
- 从应用中心进入的用户并没有 SqlBot 本地密码，看到这个页面只能再找「返回应用中心」入口，无法完成用户期望的「统一登出到 LangBot」。
- 影响所有从 `/portal` 进入 SqlBot 的用户；触发时机是 SqlBot token 过期（默认 `LANGBOT_SSO_TOKEN_TTL_MINUTES=480`，即 8 小时）或服务端使该 token 失效之后，对任意需要鉴权的接口发起请求时。

原因：

- SqlBot 是**独立 SPA**，有自己的一套登录态，不会自动感知 LangBot 的会话。它的全局 401 处理在 `frontend/src/utils/request.ts` 的 `handleError()`：普通会话弹出错误提示，2 秒后删除 `user.token` 并 `window.location.reload()`；重载后路由守卫 `frontend/src/router/watch.ts` 发现没有 token，就调用 `toLoginPage()` 跳到 SQLBot 的 `#/login`。另一条 assistant 分支则直接进入 `/401` 页面。这两条路径的终点都是 SQLBot 自己的界面。
- 聊天问答、分析、预测、推荐问题等**流式接口**走 `fetchStream()`，它用原生 `fetch` 绕过了 axios 拦截器；401 时只是流提前结束，页面留在原地，直到刷新或下一个普通接口 401 才暴露登录页。
- 应用中心会话在票据兑换成功后会写一个本地标记 `sqlbot_portal_session`（`frontend/src/utils/portal.ts` 的 `markPortalSession()`），但上述 401 路径都没有读取它，所以门户用户和直接用 SqlBot 密码登录的用户被送去了同一个 SQLBot 登录页。
- 唯一已有的跨应用退出入口是 LangBot 的 `/login?logout=1`（`web/src/app/login/page.tsx:133`）：它会调用 `clearLocalSession()` 清掉 LangBot token、`userEmail` 以及所有 `sqlbot_` 前缀的浏览器键，然后显示 LangBot 登录页。此前 SqlBot 的自动 401 流程没有调用这个入口。

证据：

```bash

grep -n "isPortalSession\\|handleError\\|toLoginPage" \\
  SQLBot/frontend/src/utils/request.ts SQLBot/frontend/src/router/watch.ts
#   request.ts:221  case 401 ... window.location.reload()
#   watch.ts:36     if (!token) next(toLoginPage(to.fullPath))

# 2) 流式接口绕过拦截器
sed -n '307,365p' SQLBot/frontend/src/utils/request.ts
#   fetchStream() 直接 fetch()，没有检查 response.status

# 3) LangBot 的统一清理入口
sed -n '128,140p' web/src/app/login/page.tsx
#   params.get('logout') === '1' -> clearLocalSession()
```

解决方案：

1. 【治本】在 SQLBot 前端集中增加 `redirectToLangbotLogout()`（`frontend/src/utils/portal.ts`），统一跳转 LangBot 的 `/login?logout=1`；在以下四条路径中，只要 `isPortalSession()` 为真就先清掉本地 token 并跳转：
   - axios 401 处理（`frontend/src/utils/request.ts` 的 `handleError()`）；
   - 流式接口 401（同一文件的 `fetchStream()`）；
   - 路由守卫发现无 token（`frontend/src/router/watch.ts`）；
   - `/401` 页面挂载时（`frontend/src/views/error/index.vue`）。
2. 【健壮性】显式「返回应用中心」的退出请求（`frontend/src/api/login.ts` 的 `logout`）改为 `customError + silent`，并在 `frontend/src/stores/user.ts` 中吞掉请求失败；即使 token 已先失效，也照常清本地状态并回 `/portal`，不会被全局 401 流程劫持成 SQLBot 登录页。
3. 【范围】只对带 `sqlbot_portal_session` 标记的会话生效；直接在 `/sqlbot/` 用本地密码登录的会话保持 SQLBot 原有 401 行为，避免把没有 LangBot 账号的用户带到 LangBot 登录页。

实际处理方案：

- 修改 SQLBot 前端 6 个文件：`utils/portal.ts`、`utils/request.ts`、`router/watch.ts`、`views/error/index.vue`、`stores/user.ts`、`api/login.ts`；新增的是门户会话 401 分支，非门户路径保持原逻辑。

- 回滚：恢复旧 SQLBot 镜像即可；该行为只在定制前端中生效，不影响 LangBot 与网关。

# 问题14：本地 Docker Desktop 下个人 Workspace 的插件 worker 起不来——nsjail 无法把宿主 bind mount 重挂为只读（2026-11-04）

- 发现时间：2026-11-04（Asia/Shanghai）
- 环境：本地 5300 栈，`langbot:local-4.11.2-ed1f62c1c801-dirty-20261104082903`（core 与 plugin runtime 同镜像），`LANGBOT_DATA_DIR=/Users/shenni/repository1/LangBot/data/docker` 以 bind mount 挂在 `/app/data`
- 状态：已修复并验证（本地改为 Docker 命名卷后插件 worker 全部恢复）

表现：

- 升级到带个人 Workspace 的新镜像后，core 日志出现 `Plugin installation c27aebb4-… failed during reconcile [dependency_prepare_failed]: Plugin dependency installer exited with code 255`（LocalAgent）和同类错误（LangRAG）；qa-analytics 无依赖，安装通过，但 worker 反复重启：runtime 日志 `[F] runChild():506 Launching child process failed`，`Plugin installation worker exited unexpectedly; restarting ee30cc4f-…`。三个插件因此都没有加载。
- 四个容器仍全部 healthy，登录、工作区列表等非插件功能正常。

原因：

- 个人 Workspace 要求插件使用 SDK 的 `shared` 运行时 profile（`src/langbot/pkg/plugin/connector.py::_resolve_runtime_profile` 在外部 WebSocket Runtime + control token 齐全时把 `auto` 解析为 `shared`）。shared profile 会把每个插件的依赖安装和 worker 进程放进 nsjail 沙箱，而 nsjail 的 chroot 根目录固定放在数据目录下：`/app/data/plugin-runtime/installations/<uuid>/root`（`worker_launcher.py::build_nsjail_args` 的 `--chroot`）。
- 本地 `/app/data` 是 macOS 宿主目录的 bind mount（Docker Desktop 的 virtiofs）。nsjail 启动时会先 bind 这个 chroot 目录，再执行 `MS_REMOUNT|MS_BIND|MS_RDONLY` 把它变成只读；virtiofs 不支持这次 remount，直接返回 `EPERM`：`mount('/run/user/nsjail.0.root', MS_REMOUNT|MS_BIND|MS_RDONLY): Operation not permitted`。nsjail 于是报 `Failed to build mount tree` → `Launching child process failed`，退出码 255。

# pid=… exited with status: 0

# 3) 同样命令，jail 根放到 /app/data（宿主 bind mount）失败

# 问题15：生产升级后三个插件全部不可用——nsjail 在容器里的权限、cgroup 和目录属主都不满足（2026-11-04）

- 发现时间：2026-11-04（Asia/Shanghai）
- 环境：生产 `http://192.168.31.66:5300`，镜像 `langbot:4.11.2-ed1f62c1c801`（core 与 plugin runtime 共用），SQLite，`shared` 插件运行时 profile
- 状态：已修复并在生产验证

表现：

- 个人 Workspace 迁移成功、登录与工作区隔离正常，但插件页三个插件（LocalAgent、LangRAG、qa-analytics）都不可用。runtime 日志每几秒重复：
  - `Plugin dependency preparation failed for installation …: Plugin dependency installer exited with code 255`（LocalAgent、LangRAG，有 `requirements.txt`）；
  - `Plugin installation worker exited unexpectedly; restarting ee30cc4f-…`（qa-analytics，无依赖）。
- 容器本身一直 healthy，健康检查 200，因此只看容器状态会误判为「已恢复」。

原因（四个条件，按发现顺序排列；前三个都会让 nsjail 以退出码 255 结束）：

1. **缺少创建命名空间的权限**：shared profile 把每个插件放进 nsjail。容器默认的 seccomp 配置会拦截 `clone(CLONE_NEWUSER|CLONE_NEWNS|…)`，日志是 `clone(...) failed: Operation not permitted`；只加 `cap_add: SYS_ADMIN` 还不够，`/proc` 也会因为 Docker 的 masked paths 挂载失败。
2. **cgroup v2 需要宿主层级**：nsjail 用 cgroup 限制内存/PID/CPU。Docker 默认的私有 cgroup 命名空间下它无法写 `cgroup.subtree_control`，报 `Couldn't setup parent cgroup (cgroupv2)`；改用 `cgroup: host` 后，容器里的 `/sys/fs/cgroup` 默认又是只读，报 `mkdir('/sys/fs/cgroup/NSJAIL.*'): Read-only file system`。
3. **历史数据目录属 uid 1001、权限 0700**：`/app/data/plugin-runtime/installations/*/root` 和 `environments/sha256` 由旧容器以 uid 1001 创建。nsjail 在新 user namespace 中以 uid 0（映射宿主 0）运行，对新 namespace 外的 inode 没有 `CAP_FOWNER`，无法执行 `chmod o+x`，报 `try 'chmod o+x' on source path: Permission denied` → `Failed to build mount tree` → 255。这不是 LangBot 代码问题，而是持久化数据目录的属主与 nsjail 的 user namespace 不匹配。
4. **离线环境缺少依赖包**：生产不能访问外网，shared profile 的依赖环境按指纹重建时必须访问本地 wheelhouse；当时 `LANGBOT_PLUGIN_PYPI_INDEX_URL` 为空、`langbot-wheelhouse` 服务未启动，因此即使权限修好，pip 仍无法下载 `langbot-plugin`、`httpx`、`PyPDF2` 等包。

一个直观的比方：nsjail 像在院子里另搭一间小屋给插件住。第一、二个问题是「门卫不让施工队进院、也不让接水电」；第三个问题是「小屋门钥匙挂在旧住户名下，新管理员打不开」；第四个问题是「屋里家具（依赖包）得从仓库搬，但仓库门没开」。

证据：

```bash
# 1) 直接在 runtime 容器里测试 nsjail
sudo docker exec langbot_plugin_runtime nsjail --mode o --chroot / -- /bin/true
# clone(flags=…CLONE_NEWUSER…): Operation not permitted   -> 需要 SYS_ADMIN + unconfined

sudo docker exec langbot_plugin_runtime nsjail --mode o --chroot / --use_cgroupv2 … -- /bin/true
# Couldn't setup parent cgroup (cgroupv2)                  -> 需要 cgroup: host
# 加 cgroup: host 后：mkdir('/sys/fs/cgroup/NSJAIL.*'): Read-only file system -> 需要可写 cgroup 绑定

# 2) 打开 nsjail verbose 后，真实失败点（临时把 --really_quiet 换成 -v）
# mount(/app/data/plugin-runtime/installations/<uuid>/root -> /run/user/nsjail.0.root//):
#   try 'chmod o+x' on source path: Permission denied
# Failed to build mount tree -> Launching child process failed

# 3) 属主确认
sudo docker exec langbot_plugin_runtime stat -c '%a %u:%g %n' \
  /app/data/plugin-runtime/installations/<uuid>/root
# 700 1001:1001
```

解决方案（已写入 `deploy/prod/docker-compose.yaml` 与 `deploy/local/docker-compose.yaml` 的 runtime 服务）：

```yaml

  - SYS_ADMIN
security_opt:
  - seccomp=unconfined
  - apparmor=unconfined
  - systempaths=unconfined
cgroup: host          # 相当于 --cgroupns=host
volumes:
  - /sys/fs/cgroup:/sys/fs/cgroup:rw
```

另外两步：

1. 修正持久化目录：`chown -R 0:0 /app/data/plugin-runtime && chmod -R a+rX /app/data/plugin-runtime`（只对 runtime 的 plugin-runtime 目录；不要对 core 的 `.venv` 或数据库做同样操作）。
2. 离线依赖：本机 `./deploy/prod/make-wheelhouse.sh` 生成 `deploy/prod/dist/wheelhouse`，上传解压到 `/opt/langbot/wheelhouse`，启用 8081 的 `langbot-wheelhouse.service`，在 `.env` 设置 `LANGBOT_PLUGIN_PYPI_INDEX_URL=http://192.168.31.66:8081/simple` 与 `LANGBOT_PLUGIN_PYPI_TRUSTED_HOST=192.168.31.66`。`deploy/prod/plugin-requirements.txt` 需要包含所有插件的依赖（本次补了 `httpx`、`langbot-plugin`、`pydantic`、`PyPDF2`、`python-docx`、`chardet`、`markdown`、`beautifulsoup4`）。

# 问题16：对话页闲置较久后发送按钮变灰、点不动——Embed Widget 的 WebSocket 重连 5 次后永久放弃（2026-11-05）

- 发现时间：2026-11-05（Asia/Shanghai）
- 环境：`/chat.html`、`/chat-jishi.html`（本地 Docker Compose `vocational-langbot-core`，镜像 `langbot:local-4.11.2-2bb1e8867395-dirty-20261104161740`；生产 `192.168.31.66:5300` 的 widget 重连逻辑一致）
- 状态：已关闭（2026-11-05 修复，单元测试 + 无头浏览器复现验证）

表现：

访客把对话页放着不操作一段时间（或电脑睡眠、服务器夜间重启）后再回来，页面和聊天记录都还在，但输入框右侧的发送按钮变成半透明灰色，点不动；输入框仍可正常输入，给人「页面没死但发不出去」的感觉。刷新页面，或把右下角聊天气泡先收起再展开，按钮立即恢复正常。两个对话页共用同一套嵌入 widget，现象一致。

原因（本节行号均指修复前版本；修复后的实现见「实际处理方案」）：

直接触发点：发送按钮的禁用状态直接绑定 WebSocket 连接状态——`updateSendBtn()` 执行 `sendBtn.disabled = !state.isConnected`（`src/langbot/templates/embed/widget.js`，修复前 `:1731`，现为 `:2032`），连接一旦断开按钮就变灰（禁用样式 `.lb-send-btn:disabled { opacity: 0.4 }` 在同文件，现 `:691`）。

机制：widget 的重连预算只有 5 次。`state.ws.onclose` 里按「3 秒 × 第几次」逐级延后重试（`widget.js:882`），即 3、6、9、12、15 秒，合计约 45 秒；第 5 次仍失败后代码不再安排任何重试，也不重置预算。因此只要「完全连不上」的时间窗超过约 45 秒，连接就永久停在断开状态。

关键坑：`state.ws.onopen` 成功时会把 `state.reconnectAttempts` 清零（`widget.js:863`）。所以「能连上但马上被断开」会无限重试；真正会耗尽预算的是**连接根本打不开**的情况——服务端停机/重启、电脑睡眠后网卡还没就绪、或 baseUrl 指向错误地址。预算用完后页面也没有任何恢复监听：`wsConnect()` 只在页面自动打开和手动展开面板时被调用（`widget.js:1737`），没有监听 `online` / `focus` / `visibilitychange`。对比同仓库 WebUI 的 WebSocket 客户端，它专门实现了这三个恢复事件（`web/src/app/infra/websocket/WebSocketClient.ts:45` 的 `recover` 与 `:121` 的注册），embed widget 没有同步这套逻辑。

一个直观的比方：重连预算像手机只剩 5 次拨号机会，每次间隔越来越长；电话一直打不通（服务端在重启/电脑刚唤醒没网）就把机会用光了，之后即使对方回拨线路恢复，手机也不会再主动拨——除非用户手动按一下「重拨」（收起再展开面板或刷新页面）。

另一个独立原因（仅本地部署会踩到）：`deploy/local/.env` 里 `LANGBOT_WEBHOOK_PREFIX=http://127.0.0.1:5300`，`serve_widget` 会把它注入成 widget 的 `baseUrl`（`src/langbot/pkg/api/http/controller/groups/pipelines/embed.py:356`、`:382`）。用局域网 IP 从**别的电脑**打开页面时，浏览器会去连它自己的 `127.0.0.1:5300`，必然失败，5 次后同样是灰按钮。生产 `.env` 注入的是 `http://192.168.31.66:5300`，正常。复核：

解决方案：

2. 【治本】把「有限次重连」改成「有上限间隔的无限重试」（如 3s 起、最大 30s），或者在第 5 次失败后保留一个低频重试定时器；避免服务器恢复后仍需人工刷新。
3. 【止血/可观测性】断开时不要只把按钮置灰：在输入区显示「连接已断开，点击重连」，点击按钮直接触发 `wsConnect()`，让访客能自救。

实际处理方案：

按「无限重试 + 恢复触发 + 心跳判活 + 可见状态」在客户端一个文件内实现，改动集中在 `src/langbot/templates/embed/widget.js`：

1. **无限重连、指数退避封顶**：删除 `maxReconnectAttempts`；`reconnectDelayMs()`（`:971`）按 `3s × 2^attempts` 计算并封顶 `30s`，另加 0–1s 随机抖动，避免服务重启后大量页面同时重连。`scheduleReconnect()`（`:978`）每次都安排下一次，永不放弃；标签页隐藏时暂停重试，改由可见性事件触发。
2. **只在认证成功时重置退避**：`onopen` 不再清零计数（原来的关键坑）；只有收到服务端 `connected` 帧（`handleWsMessage`，`:1122`）才 `reconnectAttempts = 0` 并清除待执行的重连定时器。这样「TCP 连上但马上被拒」不会再把退避锁在 3 秒，也不会误判为已恢复。
3. **恢复事件**：新增 `recoverNow()`（`:1024`），注册 `online`、`focus`、`visibilitychange`（`:2440` 附近）。联网/回到前台时立即跳过剩余退避重连；若已 `isConnected`，则先用一次强制 ping 探测（`probeConnection()`，`:1287`），没回 `pong` 就换掉「看起来还 OPEN」的僵尸连接。
4. **心跳判活**：`sendPing()`（`:1254`）每次发 `ping` 后启动 10s 超时；`handlePong()`（`:1278`）清空超时与漏答计数；连续两次漏答，或恢复事件触发的强制探测超时，就调用 `forceReconnect()`（`:995`）——先摘掉旧 socket 的事件处理器再 `close()`，避免 close 事件重复安排重连。
5. **可见状态与自救入口**：输入区上方新增 `.lb-conn-status` 按钮（CSS `:681`，DOM `:2429`），断开时显示「正在连接…」/「连接已断开，正在重连…」，点击立即重连。文案走 i18n，8 个语言目录都补了 `connecting` / `reconnecting` 两个键。
6. **主动销毁不再复活**：`wsDisconnect()`（`:1316`）由宿主 `langbotDestroy` 调用，置 `state.stopped = true` 并清定时器；展开面板是明确的用户意图，会把该标志复位后立即重试。所有 socket 回调都加了 `state.ws !== socket` 身份判断，防止旧连接的事件污染新连接。
7. **测试**：
   - 新增 `web/tests/unit/embed-widget-reconnect.test.mjs`，覆盖 5 个场景：断线后无限重试且退避封顶、认证恢复后横幅消失按钮可用、`online` 事件跳过退避、隐藏标签页不重试而恢复可见后重试、心跳两次无应答替换僵尸 socket。
   - 更新既有 `embed-widget-assistant-dedupe.test.mjs` 的假 DOM/窗口，补齐 `addEventListener`、`classList.remove/contains`。
   - `cd web && npm run test:unit`：200 项全部通过。

# 问题17：从机器人编辑页点「测试页面」打开的对话页没有【留言板】按钮（2026-11-05）

- 发现时间：2026-11-05（Asia/Shanghai）
- 环境：本地 Docker Compose `vocational-langbot-core`，镜像 `langbot:local-4.11.2-2bb1e8867395-dirty-20261104161740` → 修复后 `langbot:local-4.11.2-2bb1e8867395-dirty-20261105091500`；入口为 WebUI 机器人编辑页 →「测试页面」菜单 →「学院页面 / 技师学院页面」
- 状态：已关闭

表现：

在机器人编辑页点「测试页面」并选择学院页面后，浏览器会新开一个 `chat.html` 标签页，页面右上角看不到「留言板」按钮；而手动直接访问 `http://10.8.16.56:5300/chat.html`（地址不带 `#preview=...`）时按钮正常。招生老师因此无法在管理端自带的预览入口里试用留言板。

原因：

直接触发点：两个模板里的入口脚本在管理端预览态主动隐藏按钮——`isPreview = hashParams.has('preview') || hashParams.has('previewWelcome')`，随后 `enableLauncher()` 里执行 `if (!uuid || isPreview) return false`（`web/public/chat.html:183`、`:195`，`web/public/chat-jishi.html:189`、`:201`，修复前行号）。设计初衷是「管理员在预览页随便点几下就会写入真实线索」，但与「测试页面也要能完整试用留言板」的需求冲突。

机制：测试页面按钮由表单组件的「打开测试页」菜单实现，`openTestPage()` 会把未保存的快捷提问草稿和欢迎语草稿编码进 URL 哈希（`web/src/app/home/components/dynamic-form/DynamicFormComponent.tsx:198-215`，哈希由 `buildQuickQuestionPreviewHash` / `buildWelcomePreviewHash` 生成，见 `standaloneChatPages.ts:28-53`）。页面脚本看到哈希里带 `preview` 或 `previewWelcome` 就判定为管理员预览，把留言板入口一并隐藏。打个比方：测试页面为了让你预览「还没保存的装修图纸」，在 URL 上贴了一张「工地参观证」；留言板脚本却把「工地参观证」误当成「非真实访客」，连服务台一起撤了。

证据（Playwright 打开带预览哈希的页面）：

```text

http://10.8.16.56:5300/chat.html            → 留言板按钮存在
# 带预览哈希：按钮被隐藏
http://10.8.16.56:5300/chat.html#preview=%5B%5D&previewWelcome=%E8%8D%89%E7%A8%BF → 无留言板按钮
```

解决方案：

1. 【治本】去掉预览态隐藏逻辑：删除 `isPreview` 变量及 `enableLauncher()` 中的判断、去掉外层 `if (!isPreview)` 包裹，只保留「能找到机器人 UUID 就显示」。两个模板同步修改。
2. 【可观测性】更新 E2E：原「preview hash 下隐藏」用例改为「preview hash 下仍可用并能打开弹窗」（`web/tests/e2e/chat-page-consult.spec.ts:469`）。
3. 【权衡】代价是管理员在预览页提交留言会写入真实线索；这正是测试需要的行为，若将来要避免，应由后端标记预览来源而不是在前端藏入口。

实际处理方案：

已修改 `web/public/chat.html`、`web/public/chat-jishi.html`，删除预览态隐藏分支；`web/tests/e2e/chat-page-consult.spec.ts` 的预览用例改为断言按钮可见且弹窗可打开，18 条 E2E 全部通过。重建镜像并重启 core 后，用带 `#preview=...` 的地址（模拟 WebUI「测试页面」入口）复核：右上角「留言板」按钮可见，点击后弹窗标题、提示语和 5 个字段均正常显示，问题关闭。

# 问题18：留言板弹窗的输入框和保存按钮右侧贴边、没有内边距（2026-11-05）

- 发现时间：2026-11-05（Asia/Shanghai）
- 环境：本地 Docker Compose `vocational-langbot-core`，镜像 `langbot:local-4.11.2-2bb1e8867395-dirty-20261105091500`；页面 `/chat.html`、`/chat-jishi.html` 右上角「留言板」弹窗
- 状态：已关闭

表现：

弹窗左右留白不对称：左侧能正常看到卡片内边距，输入框和底部「保存」按钮的右边框却紧贴弹窗右边缘，看起来像被裁掉一块；5 个输入框和按钮全部如此，任何屏幕宽度下都必现。

原因：

直接触发点：输入框样式写了 `width: 100%`（`.ln-consult-field input`），但弹窗是直接挂在宿主页面 `body` 下的普通 DOM，不继承宿主页面可能存在的全局 `box-sizing: border-box` 重置；浏览器默认 `content-box`，此时 100% 只作用于内容区，再加上左右各 11px 的 `padding` 和 1px 边框，实际宽度比容器多出 24px，正好把弹窗右侧 22px 的内边距撑满并溢出。弹窗本身有 `overflow-y: auto`，横向溢出被裁掉，于是视觉上「右边没有间隙」。

打个比方：给一个正好 100cm 宽的地面铺地毯，又要求地毯左右各留 11cm 的流苏，却不允许地毯变宽——结果只能从两侧的墙面里挤，右侧墙皮就被顶掉了。

证据（Playwright 在弹窗打开时量取元素边界，单位 px）：

```text
修复前：dialogRight=842  inputRight=842  → 右侧间隙 0
修复后：dialogRight=820  inputRight=798  → 右侧间隙 22，左侧同样 22
       allInputsInside=true，保存按钮右侧间隙 22
```

解决方案：

1. 【治本】在弹窗作用域内补 `box-sizing: border-box`：`#ln-consult-dialog, #ln-consult-dialog *`，只影响弹窗内部，不污染宿主页面。
2. 【体验】输入框加 `display: block` 与边框/阴影过渡；按钮补 hover 和 `:focus-visible` 反馈；遮罩加 2px 背景模糊；弹窗加 `overscroll-behavior: contain` 防止移动端滚动穿透。

实际处理方案：

`web/public/chat.html`、`web/public/chat-jishi.html` 同步修改，重建前端并部署派生镜像 `langbot:local-4.11.2-2bb1e8867395-dirty-20261105092032`；18 条 E2E 全部通过，线上实测输入框与按钮左右间隙均为 22px，截图中弹窗左右留白对称，问题关闭。
