# LangBot 源码升级维护指南

本文说明：**在本地修改了 LangBot 源码后，如何跟随官方版本升级而不丢失自己的改动。**

核心思路不是"升级时手动搬运文件"，而是让 git 做三方合并。前提是两件事：

1. 自己的改动是**独立分支上的小颗粒 commit**，而不是堆在工作区里的一坨未提交修改；
2. 官方仓库配成 `upstream`，自己的 fork 配成 `origin`。

如果改动只是未提交的 diff，`git pull` 要么报错要么覆盖，无法自动合并。

---

## 一、仓库 remote 配置

本仓库已完成如下配置：

| remote | 地址 | 用途 |
|---|---|---|
| `origin` | `https://github.com/wandouni/LangBot.git` | 自己的 fork，用于推送定制 |
| `upstream` | `https://github.com/langbot-app/LangBot.git` | 官方仓库，只读，用于拉取升级 |

查看与校验：

```bash
git remote -v
```

**不要**把 `origin` 直接指向官方仓库 —— 那样没有推送权限，也无法把定制推上去备份。

首次推送前配置 HTTPS 凭据（本机已有 `gh`）：

```bash
gh auth setup-git
```

---

## 二、分支模型

| 分支 | 作用 | 规则 |
|---|---|---|
| `master` | 官方代码的镜像 | **永不直接提交**，只通过 fast-forward 跟随 `upstream/master` |
| `my/custom` | 本地定制的落脚点 | 所有源码定制提交到这里 |

保持 `master` 干净的意义：升级时它总是能无冲突地快进到官方最新版，冲突只会集中在 `my/custom` 上，且范围被限制在你实际碰过的那些行。

---

## 三、日常：写定制

```bash
git checkout my/custom
# ...修改源码...
git add -A
git commit -m "feat: 你的定制说明"
```

### 提交粒度要小

按**改动主题**拆分 commit，而不是攒成一个巨型 commit。例如"改了 UI 样式"和"改了消息处理流程"应当分成两组独立 commit。

这样做的好处：将来如果官方自己实现了其中某个功能，你可以整块丢掉对应的那个 commit，而不必费力从大 commit 里剥离。

---

## 四、升级：跟随官方版本

```bash
git fetch upstream
git checkout my/custom
git rebase upstream/master      # 或 merge，rebase 历史更干净
```

有冲突就逐个解决。因为你的改动是小颗粒 commit，冲突范围会被限制在实际改过的行，而不是整个文件。

升级后同步依赖：

```bash
uv sync --dev                          # 后端依赖
cd web && pnpm install && pnpm build   # 仅在改过前端时需要
```

### 让本地 master 跟到最新官方版

注意：这会把磁盘上的源码全部更新。如果当前有 LangBot 实例在跑，**重启后新代码才生效**。

```bash
git checkout master
git merge --ff-only upstream/master
```

`--ff-only` 是安全阀：如果 master 上意外出现了本地提交，该命令会直接报错而不是产生一个合并提交。

### 同步 GitHub 上的 fork

```bash
gh repo sync wandouni/LangBot
```

## 五、冲突处理

rebase 过程中出现冲突时：

```bash
git status                     # 查看冲突文件
# 手动编辑，解决冲突标记 <<<<<<< ======= >>>>>>>
git add <已解决的文件>
git rebase --continue
```

想放弃这次 rebase、回到操作前：

```bash
git rebase --abort
```

**判断原则**：如果冲突来自官方已重构你改过的那段代码，先想清楚官方的新写法是否已经满足你的需求 —— 若已满足，用 `git rebase --skip` 丢掉自己的那个 commit，比强行保留更省事。

---

## 六、降低冲突：优先不改源码

长期来看，冲突量取决于你改了多少官方文件。按维护代价从低到高：

| 需求 | 推荐落点 | 升级冲突 |
|---|---|---|
| 新业务逻辑 / 对接新平台 | 写成**插件**（独立仓库，`pkg/` 之外） | 无 |
| 改文案 / 报错信息 | `src/langbot/pkg/i18n/` 的 catalog | 极小 |
| 改默认配置值 | `data/config.yaml`（不纳入版本控制） | 无 |
| 改核心 pipeline / 适配器 | 只能改 `pkg/`，需持续维护 patch | 有，需持续 rebase |

LangBot 本身有完整的插件系统，大多数"想加个功能"的需求都能做成插件 —— 插件升级完全独立，这是最健康的路子。只有必须在 pipeline 主流程或平台适配器里插逻辑时，才需要维护源码 patch。

---

## 七、数据与配置目录

`data/` 目录（`config.yaml`、数据库等）不在 git 里，**升级不会动它**。

数据库结构变更由 Alembic 自动迁移，4.x 内部小版本升级是支持的。

> ⚠️ 注意：LangBot 4.x **不支持**从 3.x 数据库升级。跨大版本前务必备份 `data/`。

---

## 八、本机专属忽略规则

本地业务数据（如 `docs/测试问答/`）通过 `.git/info/exclude` 忽略，而不是 `.gitignore`：

```
docs/测试问答/
```

原因：`.gitignore` 是**受版本控制**的文件，改了它就意味着 `master` 永远偏离官方，每次 rebase 都要处理这一处冲突。`.git/info/exclude` 是每个 clone 私有的忽略文件，不进版本控制、不推送到 fork，效果完全一样但零冲突。

## 九、常见问题

**Q：不小心在 `master` 上提交了怎么办？**

```bash
git checkout master
git reset --hard upstream/master      # 丢弃本地提交，回到官方版本
```

若该提交有价值，先 `git cherry-pick <commit>` 到 `my/custom` 再重置。

**Q：rebase 后构建报错？**

多半是依赖没跟上，依次执行：

```bash
uv sync --dev
cd web && pnpm install && pnpm build
```

**Q：想让某个定制彻底不要了？**

```bash
git checkout my/custom
git rebase -i upstream/master         # 在交互式列表中 drop 掉对应 commit
```

**Q：`git push` 要求输入密码？**

跑一次 `gh auth setup-git`；或把 remote 换成 SSH 地址。
