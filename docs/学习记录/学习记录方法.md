# 学习记录方法

> 用途：规定 `docs/学习记录/学习记录.md` 的写入规范，并给出可直接复制的提示词。对话中出现「有疑问 / 要求解释」的内容时，按本文件沉淀为可复用的知识点。

## 一、写入规范

### 1. 文件与编号

- 目标文件：`docs/学习记录/学习记录.md`（与本文件同目录）。
- 新增条目**追加在文件末尾**，标题格式：`# 学习N：<一句话知识点>（<绝对日期>）`。
- 编号规则：若文件末尾存在占位条目（`# 学习N：xxx`），直接替换该占位；否则取现有最大编号 +1。
- 不改动、不重排历史条目；同一主题有新理解时，回填原条目或在其后补「补充」，不重复建号。
- 内容来源：只写对话中已确认的事实与结论；信息缺失时向提问者确认，不得编造；推断必须标注「推断」。
- 与[问题记录](../问题记录/问题记录.md)的分工：问题记录 = 具体事件的排查、修复与状态；学习记录 = 从中提炼的可复用知识（机制 / 原理 / 判别方法）。同一事件在两类文档间用链接引用，不整段复制。

### 2. 条目结构（信息头 + 疑问 / 解答 / 延伸）

```markdown
# 学习N：<一句话知识点>（<绝对日期>）

- 关联：<问题记录条目 / 相关文档 / 代码位置>（可选）

疑问：<提问者的原话或贴近原话的问题>

解答：
- <先结论、后机制；每个要点一句，代码引用带 文件:行号>
- <容易误判的点单独列出>

延伸：<可选：相关文档、下一步动作>
```

### 3. 各字段写作要求

| 字段   | 要求                                                                                      |
| ------ | ----------------------------------------------------------------------------------------- |
| 标题   | 一句话说清「学到了什么」，不是疑问的原标题；日期用绝对日期                                |
| 关联   | 链接到问题记录条目、代码位置或设计文档，便于追溯事件背景                                  |
| 疑问   | 用提问者原话或贴近原话，保留当时的困惑点，便于日后按原话检索                              |
| 解答   | 先结论、后机制；结论脱离上下文也能看懂；代码引用带`文件:行号`；专有名词首次出现给出来源 |
| 误判点 | 把「看起来像 A、实际是 B」写出来（如：没有日志 ≠ 没有失败）                              |
| 延伸   | 链接到问题记录、设计文档或代码；只引用、不重复其内容                                      |
| 颗粒度 | 一个条目只讲一个知识点；一个疑问牵出多个知识点就拆成多条（学习1/2/3 即如此）              |

### 4. 触发时机（什么时候写）

- 用户在对话中提出「为什么 / 是什么原因 / 怎么理解 / 怎么排查」类疑问，并已解释清楚之后；
- 用户明确说「记一下 / 记到学习记录」时；
- 一次排查结束后，把其中可复用的机制、判别方法提炼成条目（事件本身写入问题记录）。

### 5. 写法：结论用大白话，机制用专业词（硬性要求）

学习记录是给**日后忘了细节的自己**和**没参与讨论的同事**看的。既要**读得懂**，也要**留得住细节**——只讲大白话，日后照着做会做不精确；只讲术语，当时就没人看得懂。

**每一层这样写**：

1. **先讲「会发生什么」**（现象 / 结论，用大白话，脱离上下文也能看懂）；
2. **再讲「为什么会这样」**，并在这一步**原样给出关键机制**：函数名、字段名、常量、配置项、代码位置；
3. **能打比方就打比方**；
4. 必要时给**判别方法**。

**必须保留的技术锚点**（不要因为"太技术"而删掉）：

| 保留什么 | 为什么 |
|---|---|
| 关键函数 / 文件位置 | 日后要改或要复核时的入口 |
| 关键字段名、常量、配置项（如 `reasoning_content`、`iat`、`enable_thinking`、`@@unique(...)`） | 它们往往就是结论本身，删了这条记录就只剩"感觉" |
| 设计取舍 | 说明"为什么这么设计、为什么不那样做" |

**术语首次出现必须给一句解释。** 例：`iat`（JWT 里的签发时间戳）。

**合格标准（两条都要满足）**：① 没参与讨论的同事听完能转述给第三个人；② 他照着记录能**找到对应代码/配置**并动手验证。

**反面 vs 正面（取自本仓库真实疑问）**

❌ 反面一——术语堆叠，读者不知道在说什么：

> refresh token 由 `signPayload()` 签发，`iat` 精度为秒，同秒内 payload 与 `exp` 一致导致签名相同，故轮换不可观测。

❌ 反面二——只留了大白话，丢掉了关键机制，照着做不精确：

> 令牌上的时间戳精度不够，同一时间签的令牌看起来一样，所以测不出来。

✅ 正面——大白话打头，机制与字段紧随，配比方与判别方法：

> **现象**：测试里有条断言「刷新之后，旧令牌应该失效」，同一份代码跑三次——两次通过、一次失败。
> **是什么**：不是程序有 bug，而是这条断言在「同一秒内」根本观察不到变化。refresh token 是 JWT，由 `signPayload()` 签发（即 `jwt.sign(payload, secret, { expiresIn })`），其中的时间戳 `iat`（签发时刻）**只精确到秒**；而轮换时 payload 固定是 `{ id, sessionId }`（同一用户同一会话，不变），于是：
> **当两次签发落在同一秒内，签出来的令牌逐字节完全相同**——"没有轮换"是当时真实的状态，断言失败属于**测试不稳定**，不是产品缺陷。
> **打个比方**：令牌上盖的时间戳只精确到「第几秒」。前后两枚若在同一秒里盖章，连纹路都一样，自然看不出「换了一枚」。
> **怎么办**：让刷新晚一点发生（跨过整秒，测试里用 `waitPastSecondBoundary()` 等到秒数变化），断言就变成确定性的。实测连跑 4 轮全过。
> **通用的理**：**凡是要断言「某个东西应该变了」，先想清楚它「多久才会变一次」**——秒级精度的时间戳、按毫秒截断的编号、去重后的集合长度，都会让"变化"短时间内不可见，表现为"随机失败"。

## 二、提示词（复制给 Claude 使用）

> **怎么用**：与问题记录相同——在对话里把疑问聊明白后，发一句话即可，内容 AI 从当前对话里提取，不用整理粘贴。
> **最重要的要求**：**大白话打头，机制紧随**。第一句讲清学到了什么，随后给出关键机制与字段（函数名、字段名、常量、配置项、代码位置），并配一个真实例子或比方。**只堆术语看不懂、或只剩大白话找不到细节，都不合格。** 详见「一、写入规范」第 5 条。

**标准写法**

```text
把本次对话中有疑问、经过解释的内容，按 docs/学习记录/学习记录方法.md 的规范写入 docs/学习记录/学习记录.md。
注意写法：第一句用大白话讲清「学到了什么」，随后给出关键机制（函数名、字段名、常量、配置项、代码位置），配一个本次的真实例子或比方。关键字段与设计取舍要保留、首次出现时解释一句；不要写成术语堆砌，也不要写成丢掉机制的大白话。
```

**变体**

- 只记某一点：「把本次对话里关于 <主题> 的解释按规范写入学习记录。」
- 补充理解：「把学习N的后续新理解按规范回填到原条目，不要新建编号。」
- 排查后提炼：「把本次排查中可复用的机制与判别方法写到学习记录（事件本身已在问题记录，链接引用即可）。」
- **觉得现有条目看不懂**：「把学习N改写成：第一句给大白话结论，随后补上关键机制与字段（首次出现加一句解释），并配一个真实例子或比方。」
- **觉得现有条目太空、找不到细节**：「把学习N补上关键函数、字段名与配置项，同时保持大白话打头。」

执行细则（编号、结构、字段要求）统一以「一、写入规范」为准。

## 三、让记录自动发生（二选一）

- **方式一（默认，零配置）**：如第二节，对话结束前发一句提示词。
- **方式二（常驻规则，已配置）**：规则已写入项目根目录 `CLAUDE.md` 与 `AGENTS.md`，新会话自动生效、无需手动触发；调整时同步修改这两个文件的「文档记录约定」小节：

```text
对话中出现需要解释的疑问（为什么 / 是什么原因 / 怎么理解）并已解释清楚时，在回答后按 docs/学习记录/学习记录方法.md 的规范，把该疑问与解答追加到 docs/学习记录/学习记录.md；同一主题只记一次，事件类问题另走 docs/问题记录/。
```
