# 学习1：品牌色太浅时，为什么「白字读不清、黑字也发闷」，序号还发虚（2026-10-30）

- 关联：[问题1](../问题记录/问题记录.md#问题1技师学院咨询页主题蓝太浅白字与序号看不清)、`src/langbot/templates/embed/widget.js:281-420`

疑问：

用户反馈「蓝色太浅配黑色文字的时候看不清晰，序号显示也不清晰」。直觉上「浅底配黑字」应该是最安全的组合，为什么反而糊？

解答：

- **结论**：问题不在「黑字」，而在**同一个主色被同时当成底色和文字色用**，两个方向都撞上亮度极端：浅到可以当底时，它自己当字就太淡；深到可以当字时，配白字才够对比。要两头都合格，主色必须落在中间偏深的一段。
- **机制一（自动选前景色）**：widget 的 `pickOnAccent()`（`widget.js:342`）用 WCAG 相对亮度公式，在纯白 `#ffffff` 和近黑 `#111827` 之间挑对比度更大的那个。`#20bfff` 对白 2.11:1、对黑 8.41:1，所以系统**必然**选黑字。也就是说「浅蓝 + 黑字」不是配色失误，是自动选色的正确结果——但它同时暴露了另一个问题：主色已经浅到当不了「承载白字」的底色了。
- **机制二（主色当字）**：`.lb-q-index`（`widget.js:416`）直接把 accent 当序号文字色，背景是卡片 `#f9fafb`。浅蓝压浅灰只有 2.02:1，比正文还低，于是 `01`、`02` 看着发虚。**注意这一类位置不吃 `onAccent`**，改前景色救不回来，只能改主色。
- **判别方法（30 秒版）**：把候选色分别和 `#ffffff`、`#111827`、页面卡片底色 `#f9fafb` 算对比度，三项都要 ≥ 4.5（AA 正文）。`#1379B5`（院徽原色）对白 4.74 勉强过线，再压暗一档到 `#0f6fa8` 后对白 5.44、对卡片 5.21，`pickOnAccent()` 自动切到白字，`hover` 由 `mixHex(accent, 黑, 0.12)` 派生为 `#0d6294`（6.58:1），整条派生链一起达标。
- **打个比方**：主色像一块布，既当桌布又当笔芯。布太浅，写字看不清；布太深，桌面暗。真正要做的是挑一块「当桌布时白字看得见、当笔芯时也写得清」的中深色。
- **容易误判的点**：以为「黑字对比度 8.41 很高，肯定没问题」。单看一对颜色确实够，但同一页面还有「主色作字」的位置（序号、链接 hover），只检查前景色对底色会漏掉它们。

延伸：`accentHover` / `accentBorder` 一般不用手写，`widget.js:365-367` 会从主色派生；只有派生结果不满足设计要求时才显式覆盖。

# 学习2：分类提问预设存在哪、怎么改（2026-10-30）

- 关联：`web/public/chat.html:19-91`、`web/public/chat-jishi.html:22-92`、`web/public/chat-shell.js:7-14`、`src/langbot/templates/embed/widget.js:1325-1329`

疑问：

「`/chat.html` 和 `/chat-jishi.html` 的分类提问预设可修改吗，如何修改？」

解答：

- **结论**：可以改，改的是页面里那段 JSON，不是后端。两个页面各有一块 `<script type="application/json" id="chat-config">`，角色和问题都在 `roles[].questions` 里，一条一行，直接改文本即可。
- **机制一（来源与优先级）**：`chat-shell.js` 按「内联 JSON → `?config=<url>` 外部 JSON → `?embed=` / `?title=` / `?theme=`」三级合并（见文件头注释 `chat-shell.js:7-14`），最后把 `roles` 序列化进 `data-roles` 交给 widget。所以**不改代码也能换**：把同样结构的 JSON 挂到任意可访问地址，用 `?config=https://…/config.json` 覆盖；只想临时换色用 `?theme=%23RRGGBB`。
- **机制二（空数组的特殊含义）**：`["考生与家长"]` 这类角色的 `questions` 写的是 `[]`，此时 `activeRoleQuestions()`（`widget.js:1325-1329`）会回退到 `QUICK_QUESTIONS`，也就是**管理后台该页面机器人配置的快捷问题**。所以这一类要去后台改，改 HTML 没用。
- **机制三（一处改、两处显）**：同一份问题列表会同时渲染在欢迎区（`.lb-role-questions`）和底部推荐 dock，改一条两边同步；单个角色最多 5 条在窄屏下一列、宽屏三列，不会溢出。
- **操作步骤**：改 `web/public/chat.html` 或 `web/public/chat-jishi.html` → 本地 `pnpm dev` 直接生效；5300 容器里改的是 `/app/web/dist/chat.html`，需要重新 `pnpm build` 后 `docker cp`（静态文件 `no-store`，刷新即生效，不必重启）。
- **容易误判的点**：① 在 `<script type="application/json">` 里写 `//` 注释会让 `JSON.parse` 抛错，`chat-shell.js:32-35` 只打一条 warn 然后**静默回退空配置**，页面看起来像「配置没生效」而不是报错——说明文字要写到 HTML 注释里。② 改了问题但浏览器还显示旧的，先确认改的是容器里的 `/app/web/dist` 副本，而不是仓库里的 `web/public`。

# 学习3：功能开关该「关到哪里」——关掉一块功能，不等于关掉整个页面（2026-10-30）

- 关联：[问题3：关闭扩展市场后「添加扩展」整页空白](../问题记录/问题记录.md#问题3关闭扩展市场后添加扩展整页空白自定义扩展也装不了)、`web/src/app/home/add-extension/page.tsx:142`、`web/src/app/home/components/home-sidebar/HomeSidebar.tsx:1061`

疑问：

「显示不出来扩展市场吗？我想添加自定义扩展也不行。」——明明只是关了「市场」，为什么连上传本地包、加 MCP、从 GitHub 安装这些不依赖网络的功能一起没了？

解答：

- **结论**：`enable_marketplace` 这个开关的本意是「是否展示 Space 市场列表」，但前端把它用成了「整个添加扩展页面是否可用」。页面在渲染前整页 `return`，而**手动添加按钮不是独立页面，只是挂在市场页头部的一块 UI**（`<MarketPage headerActions={extensionActions} />`），所以市场一关，按钮跟着消失。
- **机制（为什么手动入口会寄生在市场页里）**：`extensionActions` 是页面里一个 React 节点（文件选择 `<input>` + `Popover` 弹层），唯一渲染位置是 `MarketPage` 的 `headerActions` 插槽。这种「公共动作作为 prop 传给某个具体视图」的写法，天然让动作的生命周期绑在那个视图上——视图不渲染，动作就没了。侧边栏的深链 `/home/add-extension?manual=1` 只是在页面挂载后执行 `setPopoverOpen(true)`，页面本身空白时它无能为力。
- **机制（首帧假象）**：`systemInfo` 是模块级对象而不是 React state，初始 `enable_marketplace: true`，等 `/api/v1/system/info` 返回后才被 `Object.assign` 改成 `false`。所以页面会先像正常页面渲染一帧，再整页变成空白——容易被误判成「接口报错/资源没加载」。这也说明：**用部署配置决定界面结构时，最好让「开关裁剪的范围」和「数据来源」解耦**，不要让一个远端返回值决定整页是否存在。
- **判别方法（写代码时的 30 秒自检）**：看到 `if (!someFlag) return <空状态/>` 包住整个组件，就问三句——① 这个 flag 的名字是否精确描述了被 return 掉的整块内容？② 页面里有没有不依赖该 flag 的功能（表单、上传、深链参数）？③ 有没有别的入口指向这个页面？三问里有一个「是」，就应该把判断下沉到子区块（本例改成 `marketplaceAvailable ? <MarketPage/> : <空状态 + extensionActions/>`）。
- **打个比方**：这就像商场某家店停业，却把整层楼的电梯也锁了——停业的是店，不是通道。开关应该锁门，而不是锁楼。
- **容易误判的点**：① 以为「页面空白」=「前端资源加载失败」，实际是新 bundle 正常执行后主动渲染的空状态，`/api/v1/system/info` 也正常返回 `enable_marketplace: false`；② 以为「打开市场开关就好了」，但该部署到 `space.langbot.app` 网络不通（实测 HTTP 000），打开只会看到一个空列表，且削弱隔离加固；③ 只检查「去市场」入口（它确实受 flag 控制，`HomeSidebar.tsx:1061`），忽略了其余手动入口是无条件跳转的，因此错误地判断为「只有市场入口受影响」。

延伸：新增回归用例的思路是「把 mock 的开关做成参数」——`web/tests/e2e/fixtures/langbot-api.ts` 加 `marketplaceEnabled`，同一条用例在两个取值下各跑一遍，开关类缺陷基本都能被这样锁住。

# 学习4：容器里的服务该写「服务名」还是「宿主机 IP」，以及连接失败要分两种（2026-10-30）

- 关联：[问题4：导入 SqlBot 导出的 MCP 配置后一直「连接失败」](../问题记录/问题记录.md#问题4导入-sqlbot-导出的-mcp-配置后一直连接失败)、`SQLBot/backend/apps/system/api/apikey.py:76`、`src/langbot/pkg/provider/tools/loaders/mcp.py:511`

疑问：

「SqlBot 导出的 MCP 配置粘进 LangBot 就连接失败，是 LangBot 不支持 SqlBot 吗？」

解答：

- **结论**：不是协议不支持，是**地址根本不存在**。导出的是 `http://192.168.31.66:8001/mcp`，而 Compose 里 SqlBot 的 8001「声明了但没发布」（`docker ps` 里是 `8000-8001/tcp`，没有 `0.0.0.0:8001->8001` 的箭头），宿主机那个端口上没人监听，所以连接直接 `ConnectError`。
- **机制一（谁生成这个地址）**：SqlBot 的 `_mcp_public_url()` 在 `MCP_PUBLIC_URL` 为空时，用「浏览器请求的 Host + `MCP_PORT`」拼地址。它看到的是用户在网关上的 `192.168.31.66:5300`，于是一个「给你家用、不对容器开放」的地址就被写进了导出 JSON。设 `MCP_PUBLIC_URL` 就绕过这段推导，直接返回固定值。
- **机制二（Compose 内的名字解析）**：同一 `networks` 下的服务可以用服务名互访，`langbot` 容器改 `sqlbot` 就等同于其容器 IP，端口也直接是容器内端口（8001）。而宿主机 IP 只有在端口「发布」到宿主机之后才通；「expose」和「ports」是两件事，前者只写文档、不开放。
- **机制三（两种「连接失败」）**：LangBot 的远程 MCP 先试 Streamable HTTP，只有收到 400/404/405 才认为「协议旧了」并回落 legacy SSE（`mcp.py:973`）。`ConnectError`/超时属于**网络层**失败，按设计不回落——所以日志里那句 `not falling back to SSE` 不是缺陷，而是在提示「地址/网络有问题」。SqlBot 的 `/mcp` 实测 `POST → 405`、`GET → text/event-stream`，正好走「先 405 再回落」这条路。
- **判别方法（30 秒版）**：在**发起连接的容器里**探测目标，而不是在宿主机或浏览器里：`docker exec -i langbot python -c "import socket; socket.create_connection(('sqlbot',8001),3)"`。通了再看 HTTP：`POST` 得 400/404/405 是协议问题，得 401/403 是 token 问题，`ConnectError` 是地址或端口问题。
- **打个比方**：服务名是楼里房间的内线分机；宿主机 IP:端口是「转到外线」的号码。没办理外线转接（发布端口），外线号码当然打不通，但内线一直好好的。
- **容易误判的点**：① 以为「浏览器能打开 `192.168.31.66:5300/sqlbot/`，所以 `192.168.31.66:8001/mcp` 也行」——5300 是网关发布的端口，8001 根本没有对外入口；② 以为是 LoadBalancer/网络策略问题去查防火墙，实际是端口没发布；③ 以为要「打开 8001 的映射」才能用，代价是把带 token 的 MCP 暴露到校园网。

延伸：修导出侧比修调用侧更稳——`deploy/prod/docker-compose.yaml` 里设 `MCP_PUBLIC_URL=http://sqlbot:8001/mcp` 之后，每次导出都是可直接导入的地址；若将来有外部 MCP 客户端，用 `.env` 的 `SQLBOT_MCP_PUBLIC_URL` 覆盖成它可访问的地址。

# 学习5：同一个模型为什么有「别名」和「完整 ID」两套名字（2026-10-30）

- 关联：[问题5：Seedream 生图 MCP 接网关必报 403](../问题记录/问题记录.md#问题5seedream-生图-mcp-接网关必报-403-model_no_authorization)、`seedream_mcp/_config_sources.py` 的 `normalize_model_selector()`、`seedream_mcp/utils/model/model_capabilities.py` 的 `MODEL_ALIASES`

疑问：

「为什么需要加白？我填 `doubao-seedream-5.0-lite` 不就是模型名吗，为什么它还去找一个叫 `doubao-seedream-5-0-260128` 的东西？」

解答：

- **结论**：模型名在系统里有**两层**。上层是给人看的**别名**（`doubao-seedream-5.0-lite`，稳定、好记），下层是平台内部的**完整 Model ID**（`doubao-seedream-5-0-260128`，带发布日期，是真正结算和路由用的标识）。包默认做「别名 → 完整 ID」的翻译，网关只认别名，两边各说各话，请求里的名字对不上就 403。
- **机制（翻译发生在启动时，不是发请求时）**：`SeedreamConfig` 构建时会调 `normalize_model_selector()`，查 `MODEL_ALIASES` 把别名替换成完整 ID 并**写回** `config.model_id`。之后所有工具拼请求体都用这个已经改写过的值。所以「配置里填别名」也只是一种输入写法，真正发出去的是完整 ID。
- **为什么握手看不出来**：`initialize` 和 `tools/list` 完全不访问网关，是本地能力协商。工具列表能列出来，只证明包装好了，不证明模型名通得过网关。真正撞上 403 的永远是第一次 `text_to_image`。
- **判别方法（30 秒版）**：`curl -H "Authorization: Bearer $KEY" https://ai.ctaigw.cn/v1/models` 看种子名单里到底有哪个名字；再在日志里搜请求体或错误里的 `model` 字段。两边字符串完全一致才可能通——大小写、点还是横线、有没有日期后缀，全要一样。
- **打个比方**：别名是「张三」，完整 ID 是「张三（工号 20260128）」。前台只登记了「张三」，你递上去一张写着工号的条子，前台说「查无此人」——不是你没被授权，是你报的名字对不上名册。
- **容易误判的点**：① 把 403 `model_no_authorization` 一律理解成「让管理员加白」；② 换了别名却忘了包会在启动时改写，以为配置改了就等于请求改了；③ 用握手成功当作「链路通」的证据。

延伸：直通开关（`SEEDREAM_MODEL_PASSTHROUGH=true`）只是把翻译这一步关掉，别名原样透传；哪天网关登记了完整 ID，关掉直通、填完整 ID 就恢复官方语义，不需要换包。

# 学习6：怎么用 `uvx` 装一个「没发到 PyPI」的补丁包（2026-10-30）

- 关联：[问题5](../问题记录/问题记录.md#问题5seedream-生图-mcp-接网关必报-403-model_no_authorization)、`scripts/setup_seedream_mcp.py` 的 `uvx_args()`、Release <https://github.com/wandouni/Seedream_MCP/releases/tag/v4.2.0.post1>

疑问：

「补丁只在 fork 里，PyPI 上没有，同事的机器怎么装？」

解答：

- **结论**：`uvx` 不只能装包名，也能直接从 wheel 的 URL 装：`uvx --from <wheel URL> <命令名>`。`--from` 指定「从哪装」，后面的 `seedream-image-mcp` 是包内声明的命令行入口，两者分开写。
- **机制**：`uvx` 相当于「临时建一个隔离环境 → 装入 → 运行」。给了 URL 就跳过 PyPI 索引，直接下载并缓存这个 wheel；同一 URL 第二次启动不会重复下载。想长期留在机器上就换成 `uv tool install --from <URL> seedream-image-mcp`，之后用 `uv tool dir --bin` 里的绝对路径启动，适合 GUI 客户端读不到 PATH 的场景。
- **版本要能看出来**：打补丁时把版本改成 `4.2.0.post1`（PEP 440 的「补丁修订」写法，比 `4.2.0` 大、比 `4.2.1` 小）。`--version` 输出这个值，就能一眼区分装的是官方版还是补丁版；文档里也靠它做「装错了」的判别。
- **别踩的坑**：MCP 客户端配置里 `command` 和 `args` 要拆开——`command` 是 uvx 的绝对路径，`args` 是 `["--from", "<URL>", "seedream-image-mcp"]`。写成一条字符串，或者把 `--from` 塞进 `command`，都会起不来。另外 `from` 后面的 URL 必须指向具体的 `.whl` 文件，指向 release 页面是下不到的。
- **打个比方**：`--from` 像「告诉快递去哪个链接取件」，后面的命令名像「取到了要拆出里面的哪个东西」。只说包名，快递会默认去 PyPI 仓库找，那里没有这份改装货。
- **容易误判的点**：① 以为必须发到 PyPI 才能给别人用；② 断网时表现为下载卡住或 `spawn_failed`，看起来像包坏了；③ 改了 fork 却没改版本号，出问题时无法确认对方装的是哪一份。

延伸：GitHub 不可达时，用 `uv tool install --from ./xxx.whl` 离线安装，或退到单文件脚本兜底；这是网络限制，不是包本身的问题。
