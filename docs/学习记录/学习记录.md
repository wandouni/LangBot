# 学习1：品牌色太浅时，为什么「白字读不清、黑字也发闷」，序号还发虚（2026-10-30）

- 关联：[问题1](../问题记录/问题记录.md#问题1技师学院咨询页主题蓝太浅白字与序号看不清)、`src/langbot/templates/embed/widget.js:281-420`

疑问：

用户反馈「蓝色太浅配黑色文字的时候看不清晰，序号显示也不清晰」。直觉上「浅底配黑字」应该是最安全的组合，为什么反而糊？

解答：

- **结论**：问题不在「黑字」，而在**同一个主色被同时当成底色和文字色用**，两个方向都撞上亮度极端：浅到可以当底时，它自己当字就太淡；深到可以当字时，配白字才够对比。要两头都合格，主色必须落在中间偏深的一段。
- **机制一（自动选前景色）**：widget 的 `pickOnAccent()`（`widget.js:342`）用 WCAG 相对亮度公式，在纯白 `#ffffff` 和近黑 `#111827` 之间挑对比度更大的那个。`#20bfff` 对白 2.11:1、对黑 8.41:1，所以系统**必然**选黑字。也就是说「浅蓝 + 黑字」不是配色失误，是自动选色的正确结果——但它同时暴露了另一个问题：主色已经浅到当不了「承载白字」的底色了。
- **机制二（主色当字）**：`.lb-q-index`（`widget.js:416`）直接把 accent 当序号文字色，背景是卡片 `#f9fafb`。浅蓝压浅灰只有 2.02:1，比正文还低，于是 `01`、`02` 看着发虚。**注意这一类位置不吃 `onAccent`**，改前景色救不回来，只能改主色。
- **判别方法（30 秒版）**：把候选色分别和 `#ffffff`、`#111827`、页面卡片底色 `#f9fafb` 算对比度，三项都要 ≥ 4.5（AA 正文）。`#1379B5`（院徽原色）对白 4.74 勉强过线，再压暗一档到 `#0f6fa8` 后对白 5.44、对卡片 5.21，`pickOnAccent()` 自动切到白字，`hover` 由 `mixHex(accent, 黑, 0.12)` 派生为 `#0d6294`（6.58:1），整条派生链一起达标。
- **打个比方**：主色像一块布，既当桌布又当笔芯。布太浅，写字看不清；布太深，桌面暗。真正要做的是挑一块「当桌布时白字看得见、当笔芯时也写得清」的中深色。
- **容易误判的点**：以为「黑字对比度 8.41 很高，肯定没问题」。单看一对颜色确实够，但同一页面还有「主色作字」的位置（序号、链接 hover），只检查前景色对底色会漏掉它们。

延伸：`accentHover` / `accentBorder` 一般不用手写，`widget.js:365-367` 会从主色派生；只有派生结果不满足设计要求时才显式覆盖。

# 学习2：分类提问预设存在哪、怎么改（2026-10-30）

- 关联：`web/public/chat.html:19-91`、`web/public/chat-jishi.html:22-92`、`web/public/chat-shell.js:7-14`、`src/langbot/templates/embed/widget.js:1325-1329`

疑问：

「`/chat.html` 和 `/chat-jishi.html` 的分类提问预设可修改吗，如何修改？」

解答：

- **结论**：可以改，改的是页面里那段 JSON，不是后端。两个页面各有一块 `<script type="application/json" id="chat-config">`，角色和问题都在 `roles[].questions` 里，一条一行，直接改文本即可。
- **机制一（来源与优先级）**：`chat-shell.js` 按「内联 JSON → `?config=<url>` 外部 JSON → `?embed=` / `?title=` / `?theme=`」三级合并（见文件头注释 `chat-shell.js:7-14`），最后把 `roles` 序列化进 `data-roles` 交给 widget。所以**不改代码也能换**：把同样结构的 JSON 挂到任意可访问地址，用 `?config=https://…/config.json` 覆盖；只想临时换色用 `?theme=%23RRGGBB`。
- **机制二（空数组的特殊含义）**：`["考生与家长"]` 这类角色的 `questions` 写的是 `[]`，此时 `activeRoleQuestions()`（`widget.js:1325-1329`）会回退到 `QUICK_QUESTIONS`，也就是**管理后台该页面机器人配置的快捷问题**。所以这一类要去后台改，改 HTML 没用。
- **机制三（一处改、两处显）**：同一份问题列表会同时渲染在欢迎区（`.lb-role-questions`）和底部推荐 dock，改一条两边同步；单个角色最多 5 条在窄屏下一列、宽屏三列，不会溢出。
- **操作步骤**：改 `web/public/chat.html` 或 `web/public/chat-jishi.html` → 本地 `pnpm dev` 直接生效；5300 容器里改的是 `/app/web/dist/chat.html`，需要重新 `pnpm build` 后 `docker cp`（静态文件 `no-store`，刷新即生效，不必重启）。
- **容易误判的点**：① 在 `<script type="application/json">` 里写 `//` 注释会让 `JSON.parse` 抛错，`chat-shell.js:32-35` 只打一条 warn 然后**静默回退空配置**，页面看起来像「配置没生效」而不是报错——说明文字要写到 HTML 注释里。② 改了问题但浏览器还显示旧的，先确认改的是容器里的 `/app/web/dist` 副本，而不是仓库里的 `web/public`。

# 学习3：功能开关该「关到哪里」——关掉一块功能，不等于关掉整个页面（2026-10-30）

- 关联：[问题3：关闭扩展市场后「添加扩展」整页空白](../问题记录/问题记录.md#问题3关闭扩展市场后添加扩展整页空白自定义扩展也装不了)、`web/src/app/home/add-extension/page.tsx:142`、`web/src/app/home/components/home-sidebar/HomeSidebar.tsx:1061`

疑问：

「显示不出来扩展市场吗？我想添加自定义扩展也不行。」——明明只是关了「市场」，为什么连上传本地包、加 MCP、从 GitHub 安装这些不依赖网络的功能一起没了？

解答：

- **结论**：`enable_marketplace` 这个开关的本意是「是否展示 Space 市场列表」，但前端把它用成了「整个添加扩展页面是否可用」。页面在渲染前整页 `return`，而**手动添加按钮不是独立页面，只是挂在市场页头部的一块 UI**（`<MarketPage headerActions={extensionActions} />`），所以市场一关，按钮跟着消失。
- **机制（为什么手动入口会寄生在市场页里）**：`extensionActions` 是页面里一个 React 节点（文件选择 `<input>` + `Popover` 弹层），唯一渲染位置是 `MarketPage` 的 `headerActions` 插槽。这种「公共动作作为 prop 传给某个具体视图」的写法，天然让动作的生命周期绑在那个视图上——视图不渲染，动作就没了。侧边栏的深链 `/home/add-extension?manual=1` 只是在页面挂载后执行 `setPopoverOpen(true)`，页面本身空白时它无能为力。
- **机制（首帧假象）**：`systemInfo` 是模块级对象而不是 React state，初始 `enable_marketplace: true`，等 `/api/v1/system/info` 返回后才被 `Object.assign` 改成 `false`。所以页面会先像正常页面渲染一帧，再整页变成空白——容易被误判成「接口报错/资源没加载」。这也说明：**用部署配置决定界面结构时，最好让「开关裁剪的范围」和「数据来源」解耦**，不要让一个远端返回值决定整页是否存在。
- **判别方法（写代码时的 30 秒自检）**：看到 `if (!someFlag) return <空状态/>` 包住整个组件，就问三句——① 这个 flag 的名字是否精确描述了被 return 掉的整块内容？② 页面里有没有不依赖该 flag 的功能（表单、上传、深链参数）？③ 有没有别的入口指向这个页面？三问里有一个「是」，就应该把判断下沉到子区块（本例改成 `marketplaceAvailable ? <MarketPage/> : <空状态 + extensionActions/>`）。
- **打个比方**：这就像商场某家店停业，却把整层楼的电梯也锁了——停业的是店，不是通道。开关应该锁门，而不是锁楼。
- **容易误判的点**：① 以为「页面空白」=「前端资源加载失败」，实际是新 bundle 正常执行后主动渲染的空状态，`/api/v1/system/info` 也正常返回 `enable_marketplace: false`；② 以为「打开市场开关就好了」，但该部署到 `space.langbot.app` 网络不通（实测 HTTP 000），打开只会看到一个空列表，且削弱隔离加固；③ 只检查「去市场」入口（它确实受 flag 控制，`HomeSidebar.tsx:1061`），忽略了其余手动入口是无条件跳转的，因此错误地判断为「只有市场入口受影响」。

延伸：新增回归用例的思路是「把 mock 的开关做成参数」——`web/tests/e2e/fixtures/langbot-api.ts` 加 `marketplaceEnabled`，同一条用例在两个取值下各跑一遍，开关类缺陷基本都能被这样锁住。

# 学习4：容器里的服务该写「服务名」还是「宿主机 IP」，以及连接失败要分两种（2026-10-30）

- 关联：[问题4：导入 SqlBot 导出的 MCP 配置后一直「连接失败」](../问题记录/问题记录.md#问题4导入-sqlbot-导出的-mcp-配置后一直连接失败)、`SQLBot/backend/apps/system/api/apikey.py:76`、`src/langbot/pkg/provider/tools/loaders/mcp.py:511`

疑问：

「SqlBot 导出的 MCP 配置粘进 LangBot 就连接失败，是 LangBot 不支持 SqlBot 吗？」

解答：

- **结论**：不是协议不支持，是**地址根本不存在**。导出的是 `http://192.168.31.66:8001/mcp`，而 Compose 里 SqlBot 的 8001「声明了但没发布」（`docker ps` 里是 `8000-8001/tcp`，没有 `0.0.0.0:8001->8001` 的箭头），宿主机那个端口上没人监听，所以连接直接 `ConnectError`。
- **机制一（谁生成这个地址）**：SqlBot 的 `_mcp_public_url()` 在 `MCP_PUBLIC_URL` 为空时，用「浏览器请求的 Host + `MCP_PORT`」拼地址。它看到的是用户在网关上的 `192.168.31.66:5300`，于是一个「给你家用、不对容器开放」的地址就被写进了导出 JSON。设 `MCP_PUBLIC_URL` 就绕过这段推导，直接返回固定值。
- **机制二（Compose 内的名字解析）**：同一 `networks` 下的服务可以用服务名互访，`langbot` 容器改 `sqlbot` 就等同于其容器 IP，端口也直接是容器内端口（8001）。而宿主机 IP 只有在端口「发布」到宿主机之后才通；「expose」和「ports」是两件事，前者只写文档、不开放。
- **机制三（两种「连接失败」）**：LangBot 的远程 MCP 先试 Streamable HTTP，只有收到 400/404/405 才认为「协议旧了」并回落 legacy SSE（`mcp.py:973`）。`ConnectError`/超时属于**网络层**失败，按设计不回落——所以日志里那句 `not falling back to SSE` 不是缺陷，而是在提示「地址/网络有问题」。SqlBot 的 `/mcp` 实测 `POST → 405`、`GET → text/event-stream`，正好走「先 405 再回落」这条路。
- **判别方法（30 秒版）**：在**发起连接的容器里**探测目标，而不是在宿主机或浏览器里：`docker exec -i langbot python -c "import socket; socket.create_connection(('sqlbot',8001),3)"`。通了再看 HTTP：`POST` 得 400/404/405 是协议问题，得 401/403 是 token 问题，`ConnectError` 是地址或端口问题。
- **打个比方**：服务名是楼里房间的内线分机；宿主机 IP:端口是「转到外线」的号码。没办理外线转接（发布端口），外线号码当然打不通，但内线一直好好的。
- **容易误判的点**：① 以为「浏览器能打开 `192.168.31.66:5300/sqlbot/`，所以 `192.168.31.66:8001/mcp` 也行」——5300 是网关发布的端口，8001 根本没有对外入口；② 以为是 LoadBalancer/网络策略问题去查防火墙，实际是端口没发布；③ 以为要「打开 8001 的映射」才能用，代价是把带 token 的 MCP 暴露到校园网。

延伸：修导出侧比修调用侧更稳——`deploy/prod/docker-compose.yaml` 里设 `MCP_PUBLIC_URL=http://sqlbot:8001/mcp` 之后，每次导出都是可直接导入的地址；若将来有外部 MCP 客户端，用 `.env` 的 `SQLBOT_MCP_PUBLIC_URL` 覆盖成它可访问的地址。

# 学习5：同一个模型为什么有「别名」和「完整 ID」两套名字（2026-10-30）

- 关联：[问题5：Seedream 生图 MCP 接网关必报 403](../问题记录/问题记录.md#问题5seedream-生图-mcp-接网关必报-403-model_no_authorization)、`seedream_mcp/_config_sources.py` 的 `normalize_model_selector()`、`seedream_mcp/utils/model/model_capabilities.py` 的 `MODEL_ALIASES`

疑问：

「为什么需要加白？我填 `doubao-seedream-5.0-lite` 不就是模型名吗，为什么它还去找一个叫 `doubao-seedream-5-0-260128` 的东西？」

解答：

- **结论**：模型名在系统里有**两层**。上层是给人看的**别名**（`doubao-seedream-5.0-lite`，稳定、好记），下层是平台内部的**完整 Model ID**（`doubao-seedream-5-0-260128`，带发布日期，是真正结算和路由用的标识）。包默认做「别名 → 完整 ID」的翻译，网关只认别名，两边各说各话，请求里的名字对不上就 403。
- **机制（翻译发生在启动时，不是发请求时）**：`SeedreamConfig` 构建时会调 `normalize_model_selector()`，查 `MODEL_ALIASES` 把别名替换成完整 ID 并**写回** `config.model_id`。之后所有工具拼请求体都用这个已经改写过的值。所以「配置里填别名」也只是一种输入写法，真正发出去的是完整 ID。
- **为什么握手看不出来**：`initialize` 和 `tools/list` 完全不访问网关，是本地能力协商。工具列表能列出来，只证明包装好了，不证明模型名通得过网关。真正撞上 403 的永远是第一次 `text_to_image`。
- **判别方法（30 秒版）**：`curl -H "Authorization: Bearer $KEY" https://ai.ctaigw.cn/v1/models` 看种子名单里到底有哪个名字；再在日志里搜请求体或错误里的 `model` 字段。两边字符串完全一致才可能通——大小写、点还是横线、有没有日期后缀，全要一样。
- **打个比方**：别名是「张三」，完整 ID 是「张三（工号 20260128）」。前台只登记了「张三」，你递上去一张写着工号的条子，前台说「查无此人」——不是你没被授权，是你报的名字对不上名册。
- **容易误判的点**：① 把 403 `model_no_authorization` 一律理解成「让管理员加白」；② 换了别名却忘了包会在启动时改写，以为配置改了就等于请求改了；③ 用握手成功当作「链路通」的证据。

延伸：直通开关（`SEEDREAM_MODEL_PASSTHROUGH=true`）只是把翻译这一步关掉，别名原样透传；哪天网关登记了完整 ID，关掉直通、填完整 ID 就恢复官方语义，不需要换包。

# 学习6：怎么用 `uvx` 装一个「没发到 PyPI」的补丁包（2026-10-30）

- 关联：[问题5](../问题记录/问题记录.md#问题5seedream-生图-mcp-接网关必报-403-model_no_authorization)、`scripts/setup_seedream_mcp.py` 的 `uvx_args()`、Release <https://github.com/wandouni/Seedream_MCP/releases/tag/v4.2.0.post1>

疑问：

「补丁只在 fork 里，PyPI 上没有，同事的机器怎么装？」

解答：

- **结论**：`uvx` 不只能装包名，也能直接从 wheel 的 URL 装：`uvx --from <wheel URL> <命令名>`。`--from` 指定「从哪装」，后面的 `seedream-image-mcp` 是包内声明的命令行入口，两者分开写。
- **机制**：`uvx` 相当于「临时建一个隔离环境 → 装入 → 运行」。给了 URL 就跳过 PyPI 索引，直接下载并缓存这个 wheel；同一 URL 第二次启动不会重复下载。想长期留在机器上就换成 `uv tool install --from <URL> seedream-image-mcp`，之后用 `uv tool dir --bin` 里的绝对路径启动，适合 GUI 客户端读不到 PATH 的场景。
- **版本要能看出来**：打补丁时把版本改成 `4.2.0.post1`（PEP 440 的「补丁修订」写法，比 `4.2.0` 大、比 `4.2.1` 小）。`--version` 输出这个值，就能一眼区分装的是官方版还是补丁版；文档里也靠它做「装错了」的判别。
- **别踩的坑**：MCP 客户端配置里 `command` 和 `args` 要拆开——`command` 是 uvx 的绝对路径，`args` 是 `["--from", "<URL>", "seedream-image-mcp"]`。写成一条字符串，或者把 `--from` 塞进 `command`，都会起不来。另外 `from` 后面的 URL 必须指向具体的 `.whl` 文件，指向 release 页面是下不到的。
- **打个比方**：`--from` 像「告诉快递去哪个链接取件」，后面的命令名像「取到了要拆出里面的哪个东西」。只说包名，快递会默认去 PyPI 仓库找，那里没有这份改装货。
- **容易误判的点**：① 以为必须发到 PyPI 才能给别人用；② 断网时表现为下载卡住或 `spawn_failed`，看起来像包坏了；③ 改了 fork 却没改版本号，出问题时无法确认对方装的是哪一份。

延伸：GitHub 不可达时，用 `uv tool install --from ./xxx.whl` 离线安装，或退到单文件脚本兜底；这是网络限制，不是包本身的问题。

# 学习7：MCP 配置里的 `seedream` 是服务名，不是工具名（2026-11-02）

- 关联：[豆包Seedream生图MCP-同事提示词.md](../豆包Seedream生图MCP-同事提示词.md)、WorkBuddy 日志 `~/.workbuddy/logs/`、`~/.workbuddy/mcp-tool-list.json`

疑问：

「`seedream__text_to_image` 这个名字哪里来的？AI 配置好后是这个名字吗？我看到的 MCP 名字是 `seedream`。」

解答：

- **结论**：`seedream` 是 **MCP 服务名**（配置里写作 `mcpServers.seedream` 或 `[mcp_servers.seedream]`），不是工具名。工具本身叫 `text_to_image`；客户端给模型看的完整名是 `mcp__<服务名>__<工具名>`，即 **`mcp__seedream__text_to_image`**。单独的 `seedream__text_to_image` 不是实际名字，只是完整名去掉 `mcp__` 前缀后的写法，容易让人误以为它是另一个工具。
- **机制**：MCP 协议握手和 `tools/list` 返回的是工具**裸名**（`text_to_image`），命名空间由客户端补。客户端统一拼成 `mcp__` + 服务名 + `__` + 工具名，避免不同 server 的同名工具冲突。本机实测：WorkBuddy 日志里是 `executeMcpTool: tool=mcp__seedream__text_to_image serverName=seedream`；WorkBuddy 会话里列出的 6 个工具全部是 `mcp__seedream__*`。Claude Code 的约定也是 `mcp__<server>__<tool>`；Codex 二进制中能搜到 `mcp__server__tool` 的格式串（推断同为该格式，最终以它实际 `tools/list` 为准）。
- **判别方法**：看工具列表或调用日志里的全名——`serverName=seedream` 只说明服务名，`tool=` 后面才是完整工具名；配置里的 `seedream` 只决定前缀，不决定工具名。让 AI 报一次实际 `tools/list`，比照着名字猜可靠。
- **打个比方**：`seedream` 是科室名，`text_to_image` 是医生名；模型看到的完整称呼是「科室 + 医生」。只说科室名，模型不知道具体叫谁；把科室名和医生名拼错前缀，模型也会找错人。
- **容易误判的点**：① 把配置里的 `seedream` 当成工具名；② 把 `seedream__text_to_image` 当独立名字，少写 `mcp__` 后模型只能模糊匹配，甚至转去用内置生图；③ 以为 Claude Code、Codex、WorkBuddy 三端名字一定不同，实际都遵循 `mcp__<server>__<tool>`，但仍应以各自工具列表为准。

延伸：[豆包Seedream生图MCP-同事提示词.md](../豆包Seedream生图MCP-同事提示词.md) 中的示例提问已统一改为 `mcp__seedream__text_to_image`，并要求 AI 在最终结论里报告实际完整工具名。

# 学习8：页面角色问题和后台快捷提问，谁覆盖谁（2026-11-02）

- 关联：[对外咨询页面访问指南](../对外咨询页面访问指南.md)、`src/langbot/templates/embed/widget.js:1385-1389`、`web/public/chat.html:32`、`web/public/chat-jishi.html:43-106`、`src/langbot/pkg/api/http/controller/groups/pipelines/embed.py:43-78`

疑问：

「机器人配置界面的快捷提问框配置还有用吗，chat.html 和 chat-jishi.html 的 roles 好像是写死了？」

解答：

- **结论**：后台快捷提问没有废弃，但它是**兜底**，不是总开关。优先级是「当前角色自带的 `questions` → 没有就用后台快捷提问 → 两边都空就不显示」。
- **机制（兜底发生在哪）**：`activeRoleQuestions()`（`widget.js:1385-1389`）只有两行逻辑：`if (!ROLES.length) return QUICK_QUESTIONS;`，否则 `role && role.questions.length ? role.questions : QUICK_QUESTIONS`。`QUICK_QUESTIONS` 来自后端注入的机器人配置 `quick_questions`（`embed.py:331-335`），后台最多保留 12 条、每条 200 字（`embed.py:43-78`）。
- **机制（两个页面的现状）**：`chat.html` 只有「考生与家长」是 `[]`（`chat.html:32`），所以只有这个默认角色显示后台快捷提问，其余 5 个角色显示页面里写死的五条；`chat-jishi.html` 六个角色全部写了固定问题（`chat-jishi.html:43-106`），因此**后台快捷提问在这个页面完全不出现**。
- **机制（后台快捷提问还在哪些地方生效）**：① 外部网站用的标准挂件不传 `data-roles`，走 `createQuickQuestionButtons()`（`widget.js:1699-1701`）和底部 quick dock（`widget.js:2120`）；② 任何 `questions: []` 的角色；③ `?config=` 远程配置里没写 `roles` 或写了空数组；④ 向导里的页面机器人测试挂件只传 `title`、不传 `data-roles`（`web/src/app/wizard/page.tsx:1512-1545`），看的也是后台快捷提问。
- **判别方法（30 秒版）**：打开页面，看最左侧默认角色的问题是否与后台一致；在后台改一条问题，等 5 分钟（`widget.js` 带 `max-age=300`）刷新，看哪个角色变了。更直接的办法是打开页面 HTML 看 `roles[].questions` 是否为空数组。
- **打个比方**：后台快捷提问是「默认菜单」，页面角色问题是「各窗口的专属菜单」。窗口没写菜名时才轮到默认菜单；窗口写了，默认菜单再改也不会出现在这个窗口。
- **容易误判的点**：① 后台改了页面没变，就以为是缓存或 bug，实际是该页所有角色都写死了；② 以为页面写死就完全不能用后台维护，其实把 `questions` 改成 `[]` 就能交回后台；③ 多个空角色共享同一份后台列表，后台做不到「每个角色不同问题」，要区分只能写在页面 JSON 或远程 `?config=`。

延伸：想后台可维护，就把对应角色的 `questions` 改成 `[]`；想按角色区分，就保留页面 JSON。具体链接写法见 [对外咨询页面访问指南](../对外咨询页面访问指南.md) 的「场景 D」。

**更新（2026-11-02，分类快捷提问上线后）**：

- **结论变了**：后台现在可以直接配置「快捷提问分类」，此时优先级变成「后台分类 → 页面 `roles` → 后台默认快捷提问」。只要后台分类非空，页面里写死多少个角色都不再参与渲染。
- **机制**：新字段 `adapter_config.quick_question_groups` 由 `_parse_quick_question_groups()`（`embed.py:83-140`）清洗后注入 `__LANGBOT_ROLE_GROUPS__`；挂件在 `widget.js:280-282` 先读后台分类，没有才退回页面 `data-roles`。每个分类仍走 `activeRoleQuestions()`（`widget.js:1385-1389`）的兜底：分类里没有问题时用默认快捷提问。
- **判别方法（更新版）**：打开机器人配置看「快捷提问分类」是否有内容。有内容 → 页面角色被忽略；为空 → 才回到上面那套「角色问题 vs 默认快捷提问」的判断。
- **比方**：原先后台只有「默认菜单」，页面角色是「各窗口专属菜单」；现在后台多了一本「整本替换的新菜单」——只要这本菜单存在，各窗口的专属菜单就全部收起来，只剩新菜单里的分类。
- **改动入口**：控制台 → 机器人 → 适配器配置 → 快捷提问分类；最多 6 类、每类 12 条、每条 200 字。具体操作和例子见 [对外咨询页面访问指南](../对外咨询页面访问指南.md) 的「场景 E」。

**更新（2026-11-03，移除旧快捷提问兜底并改为文本编辑）**：

- **结论再变一次**：旧的「每行一个快捷提问」`quick_questions` 不再参与任何渲染，也不再作为空分类/无分类的兜底。现在只有两层：后台「快捷提问分类」有内容 → 用后台分类；否则用页面 `data-roles`。页面某个角色的 `questions: []` 就是真的空，不再借用其他来源。
- **机制（删了哪些链路）**：`web_page_bot.yaml` 删除了 `quick_questions` 字段；`embed.py` 删除了 `_parse_quick_questions()` 和对 `__LANGBOT_QUICK_QUESTIONS__` 的注入；`widget.js` 删除了 `CONFIG.quickQuestions`、`QUICK_QUESTIONS` 以及非角色页面的底部 quick dock。`activeRoleQuestions()`（`widget.js:1356-1359`）现在只返回当前角色的 `questions`，空数组直接返回 `[]`。
- **文本编辑格式**：后台分类编辑器从「分类 Tab + 添加按钮」改成一个大文本框。每个分类名单独一行，下面每行一个问题，空一行分隔下一个分类；分类名后的冒号可有可无。解析/序列化在 `quickQuestionGroupsText.ts` 的 `parseQuickQuestionGroupsText()` / `serializeQuickQuestionGroups()`，组件是 `QuickQuestionGroupsEditor.tsx`。解析时会去重、截断超长内容，并限制 6 个分类、每类 12 条。
- **数据库遗留值**：老机器人 `adapter_config.quick_questions` 里可能还有 12 条旧数据；字段删了但数据没删，后端读取时直接忽略。要彻底清理可以另行写迁移，但不影响访客端。
- **比方**：原先后台有「默认菜单」和「新菜单」两本，空窗口会去翻默认菜单；现在默认菜单被收走，只保留「新菜单」和页面自己印的菜单。新菜单没写菜名的窗口，就真的空着，不会再端出旧默认菜。

**更新（2026-11-03，页面角色也移除，测试页改看草稿）**：

- **结论第三次调整**：页面 `roles` 这层兜底也删掉了。现在普通访客页面的快捷提问只有一个来源——机器人后台保存的「快捷提问分类」；后台没配就是没有 Tab，不会恢复页面里写死的角色。
- **机制（预览怎么绕过“未保存”）**：后台「测试页面」按钮在 `DynamicFormComponent.openTestPage()` 里读取当前表单值 `quick_question_groups`，用 `buildQuickQuestionPreviewHash()` 编码成 URL 锚点 `#preview=...`。`chat-shell.js` 读到后给挂件脚本加 `data-preview-roles="true"` 和 `data-roles="..."`；`widget.js` 用 `ROLES = data-preview-roles ? PREVIEW_ROLES : BOT_ROLES`，所以草稿优先，空草稿也会覆盖已保存分类。
- **为什么用 URL 锚点而不是查询参数**：锚点不会发送给服务器，6 个分类 × 12 个问题 × 200 字的大草稿不会撑爆请求头，也不会触发 414 或代理长度限制；同时新窗口能直接拿到这份一次性数据。
- **判别方法**：测试页 URL 带 `#preview=` 时，看的就是后台文本框当前内容；URL 没有 `#preview=` 时，看的是已保存配置。公开分享的链接不要带 `#preview=`，否则访客会看到当时那份草稿。
- **比方**：以前「测试页面」是让访客走进店里看已经贴好的菜单；现在测试按钮会把厨师手里还没贴出去的草稿菜单直接塞给这一桌，其他人看到的仍是墙上已保存的那份。

# 学习9：为什么 SqlBot 退出登录后，不能用 LangBot 的账号密码登录（2026-11-03）

- 关联：`deploy/portal/README.md`（已知限制）、`src/langbot/pkg/api/http/service/sqlbot_sso.py`、`SQLBot/backend/apps/system/api/langbot_sso.py:205-245`

疑问：

「LangBot 登录之后进入应用中心，再进入 SqlBot，SqlBot 退出登录之后回到 SQLBot 主界面，为什么不能用之前在 LangBot 那边使用的账号进行登录？」

解答：

- **结论**：LangBot 和 SqlBot 是两套独立的账号库；应用中心的「免密进入」只是拿一次性票据换 SqlBot token，**从来没有把 LangBot 的密码同步给 SqlBot**。所以在 SqlBot 登录页输入同名账号 + LangBot 密码，一定对不上。
- **机制一（SSO 只传名字，不传密码）**：LangBot 的 `SqlbotSsoService.issue_ticket()` 只把 `account`、`account_uuid`、`binding_hash` 发给 SqlBot（`src/langbot/pkg/api/http/service/sqlbot_sso.py` 的 `issue_ticket`），请求体里没有密码字段。
- **机制二（SqlBot 自动建号时给的是随机密码）**：`_resolve_or_create_user()`（`SQLBot/backend/apps/system/api/langbot_sso.py:205-245`）按 `account` 查找本地用户；找不到就新建，密码写死为 `md5pwd(secrets.token_urlsafe(32))`——32 字节随机数，**任何人（包括管理员）都不知道明文**，也从未展示过。
- **机制三（密码登录怎么校验）**：SqlBot 登录页 `/login/access-token` 调 `authenticate()`（`SQLBot/backend/apps/system/crud/user.py:53-59`），把输入的密码做 MD5 后与库里的 `password` 比对。LangBot 的密码根本不在这张表里，所以必然失败。
- **机制四（为什么退出后才暴露）**：从应用中心进入时走的是 `exchange_ticket()`（`SQLBot/backend/apps/system/api/langbot_sso.py:292-345`），用票据直接签发 token，登录页根本没参与。退出只清掉 SqlBot 自己的 token，而票据是**一次性**的（兑换时 `_ticket_store.pop(ticket_hash)`），不能再拿来登录。
- **正确做法**：不需要在 SqlBot 登录页猜密码。回到 LangBot 的 `/portal` 应用中心，再点一次「SqlBot」，LangBot 会重新签一张票，仍然免密进入。两套系统没有单点退出（`deploy/portal/README.md` 的「已知限制」），SqlBot 退出不影响 LangBot 会话。
- **如果确实要密码登录**：得由 SqlBot 管理员在该系统内给这个 `account` 重置密码；LangBot 密码永远不适用。另外 SSO 新建的账号权限是 `weight=0`（`_ensure_membership()` 里写死），可能看不到数据源，需要单独提权。
- **容易误判的点**：① 以为「同一个用户名」就是同一个账号——SSO 匹配键是 `account` 字符串（大小写不敏感），`account_uuid` 虽然发了但当前 SqlBot 侧没用到；② 以为退出会联动 LangBot——实际只退出 SqlBot；③ SqlBot 会拒绝接管 `admin`（id=1）或 `origin != 0` 的账号（`_check_existing_user()`）。
- **打个比方**：应用中心像公司前台发的一张「今天有效的一次性访客卡」，刷卡就能进 SqlBot 的门，退场时卡被收回。登录页要的是 SqlBot 自己发的工牌密码，而前台从没把 LangBot 的工牌密码交给 SqlBot。

延伸：若希望「从 SqlBot 退出就一并退出 LangBot」，目前没有实现，需要另行设计跨系统单点退出；当前设计取舍是让两边会话互不影响，避免一侧退出把另一侧正在进行的问数打断。

**更新（2026-11-03，退出语义调整后）**：

- **行为变了**：从应用中心进入的 SqlBot 会话，退出入口文案改为「返回应用中心」；点击后只结束 SqlBot 会话并回到 `/portal`，**LangBot 登录保持有效**。需要完全退出时，用应用中心右上角的「退出」。
- **机制**：`markPortalSession()` 在票据兑换成功时写入 `sqlbot_portal_session` 标记；`userStore.logout()`（`SQLBot/frontend/src/stores/user.ts`）读到标记后，清掉标记并跳转 `PORTAL_HOME_URL`（`/portal`）。非门户会话（直接密码登录）仍按 SqlBot 原逻辑回登录页。
- **为什么不保留「退出登录」文案**：若文案仍写「退出登录」却保留 LangBot 会话，用户在共用电脑上会误以为已完全退出。语义与行为必须一致：应用内退出 = 返回启动器；全局退出 = 应用中心右上角。
- **兼容性**：LangBot 的 `/login?logout=1` 强制清理入口保留，旧版 SqlBot 仍可调用；LangBot 与 SqlBot 镜像可以分开升级。

# 学习10：为什么只更新前端，后台配置页还是旧字段（2026-11-03）

- 关联：[问题6：只更新前端 `dist` 后页面机器人看不到「快捷提问分类」](../问题记录/问题记录.md)、`src/langbot/pkg/platform/sources/web_page_bot.yaml`、`web/src/app/infra/form/dynamic.ts`
- 关联代码：`GET /api/v1/platform/adapters`、`DynamicFormItemType.QUICK_QUESTION_GROUPS`

疑问：

「分类快捷提问的前端已经重新构建并同步进容器了，为什么机器人编辑页还是只有原来那个每行一个的快捷提问框？」

解答：

- **结论**：这个页面不是「前端写死字段」，而是**后端下发字段清单、前端只负责按类型渲染**。字段清单来自 `web_page_bot.yaml`，没同步后端文件，前端再新也没有字段可画。
- **机制一（前端只认识类型）**：`DynamicFormItemType.QUICK_QUESTION_GROUPS = 'quick-question-groups'`（`web/src/app/infra/form/dynamic.ts`）只是告诉前端「遇到这个类型时用 `QuickQuestionGroupsEditor` 渲染」。真正的 `name / label / description / default` 由后端适配器定义提供。
- **机制二（字段清单从后端来）**：页面机器人编辑页调用 `GET /api/v1/platform/adapters`，读取 `web_page_bot.spec.config`；后端用 `src/langbot/pkg/platform/sources/web_page_bot.yaml` 生成这份 JSON。YAML 里没有 `quick_question_groups`，接口里就没有，前端自然不显示。
- **机制三（容器里的源码是镜像副本）**：容器以 editable 方式安装 `/app`，`langbot.__file__` 指向 `/app/src/langbot/__init__.py`，运行的是**镜像里的源码**，不是宿主机仓库的 `src/`。所以只替换 `/app/web/dist` 不会改变后端 YAML/Python。
- **判别方法**：登录后调 `GET /api/v1/platform/adapters`，看 `web_page_bot.spec.config` 里有没有目标字段。没有 → 后端没更新；有但页面不显示 → 才去查前端 bundle 或浏览器缓存。本次修复前就是前者。
- **运行链路也一样**：`quick_question_groups` 不只在后台表单出现，访客端还要靠 `embed.py` 解析、`widget.js` 的 `roleGroups` 注入。三份文件（YAML、`embed.py`、`widget.js`）缺一份，表现就会不同：缺 YAML 是后台看不到，缺后两份是后台能填但访客端不生效。
- **打个比方**：前端是印刷厂，只会按「表单模板」印表；模板本身放在后端 YAML 里。只把印刷机升级了，却没换模板，印出来的当然还是旧表格。
- **容易误判的点**：① 以为「页面刷新没变化 = 浏览器缓存」，反复强刷；② 以为前端构建产物包含后端配置，只同步 `dist`；③ 以为容器挂载了整个仓库，实际上这次只挂了 `data/`，`/app/src` 是镜像内容。

# 学习11：应用中心的「不可用」不是探活，而是配置三件套 + 同源网关（2026-11-03）

- 关联：[问题8：本地 5300 应用中心的 SqlBot 卡片一直显示「不可用」](../问题记录/问题记录.md)、`src/langbot/pkg/api/http/service/sqlbot_sso.py`、`web/src/app/portal/page.tsx:124`、`deploy/portal/nginx.conf`

疑问：

「应用中心里的 SqlBot 为什么显示不可用？能不能把它勾成可用？」

解答：

- **结论**：那个灰按钮不是健康检查的结果，也没有后台勾选框；它由 `/api/v1/system/info` 返回的 `portal.sqlbot_enabled` 决定。该值只有在「应用中心开启 + SqlBot 卡片开启 + SSO 握手配置有效」三者同时满足时才为 `true`。
- **机制一（前端只看一个布尔值）**：`PortalPage` 用 `sqlbotEnabled = systemInfo.portal?.sqlbot_enabled === true`（`web/src/app/portal/page.tsx:124`）控制按钮是否禁用，不会去探测 SqlBot 端口。所以「SqlBot 进程活着」和「卡片可用」是两回事。
- **机制二（后端的三件套）**：`SqlbotSsoService.settings()` 里 `enabled = portal_enabled && sqlbot_enabled && handoff_enabled`；`handoff_enabled` 还要求 `sqlbot.base_url` 合法、`context_path` 合法、`sso.shared_secret` 长度 ≥16。少一项，`/system/info` 就继续报 `false`，只改 `sqlbot_enabled` 并不够。
- **机制三（必须同源）**：LangBot 签完票返回的跳转地址是相对路径 `/sqlbot/#/login?sso_ticket=...`（`issue_ticket()` 里 `redirect_url`）。浏览器会回到当前站点的 `/sqlbot/`，因此 5300 必须有一个网关把 `/sqlbot/` 转给 SqlBot；没有网关时，这个路径会被 LangBot 的 SPA 兜底，打开的还是 LangBot 自己。
- **机制四（内部开票接口要藏起来）**：LangBot 用 Compose 内网地址 `http://sqlbot:8000` 直连 SqlBot 的 `/sqlbot/api/v1/system/langbot/sso/ticket`；网关则对浏览器把这个路径直接返回 404，避免票据接口暴露。这也是为什么「浏览器能开 `/sqlbot/`」不代表「浏览器能开票据接口」。
- **判别方法（30 秒版）**：① `curl /api/v1/system/info` 看 `portal.sqlbot_enabled`；② 看 `curl /sqlbot/` 的 `<title>` 是 `SQLBot` 还是 `LangBot`（后者说明没有网关/代理）；③ 不带签名 `POST .../sso/ticket`：`401` = SSO 已启用，`503` = SSO 关闭，`404` = 路由不存在或代码没进镜像。
- **镜像陷阱（这次踩到的）**：旧容器里有的文件不等于镜像里有。此前为联调 `docker cp`/`exec` 写进 `/app/src` 与 `/opt/sqlbot/app` 的补丁，容器一重建就消失；用 `docker run --rm --entrypoint sh <image> -lc 'find / -name sqlbot_sso.py'` 可以直接验证镜像本身是否带功能。
- **打个比方**：`portal.sqlbot_enabled` 像前台的「是否开放这条通道」告示牌；SSO 密钥和 base_url 是门禁读卡器；`/sqlbot/` 网关是真正通往 SqlBot 的走廊。告示牌写着「开放」、读卡器也装好了，但走廊没修，客人还是过不去。
- **容易误判的点**：① 以为按钮灰 = SqlBot 宕机，去重启 SqlBot；② 以为改一个 YAML 开关就能用，忽略 SSO 密钥/地址；③ 以为端口映射到了宿主机就能被浏览器和容器同时访问，忽略 Docker 网络里要用服务名；④ 重建容器后才发现镜像里没有之前手工拷进去的代码。
- **持久化提醒（本轮补完）**：「镜像 + `docker cp`」只能算热补丁，`docker restart` 不丢、`docker rm` 重建必丢。要确认运行环境到底和镜像差了什么，可以起一个同镜像临时容器，对 `/app/src`、`/app/web/dist` 做 sha256 清单比对；本轮比对结果恰好只有 `embed.py`、`web_page_bot.yaml`、`widget.js` 三份后端文件和前端构建产物不同，与 `git diff --stat -- src` 对得上。长期应以工作树 `docker build` 新镜像或先提交再构建，别把 `docker cp` 当发布方式。
- **根治机制（本地栈已落地）**：Docker 容器由「只读镜像层 + 可写容器层」组成，`docker cp` 改的是可写层，`docker rm`/Compose 重建时这一层整体丢弃；把代码放进镜像层，重建才会稳定复现。`deploy/local/docker-compose.yaml` 把 4 个容器、网络别名、端口、挂载和健康检查都写成文件；`build-image.sh` 从当前工作树构建带日期脏标记的镜像并写回 `.env`；`deploy.sh` 只重建核心、`--all` 重建整栈。日常工作流固定为「改代码 → `build-image.sh` → `deploy.sh`」。
- **怎么确认「镜像真的等于工作树」**：不要看容器里文件存在就放心，直接比哈希：`docker exec <容器> sha256sum /app/<路径>` 与宿主机 `shasum -a 256 <路径>` 对照。本轮重建后 `embed.py`、`web_page_bot.yaml`、`widget.js` 三份全部 `MATCH`；若不一致，说明构建上下文和当前工作树不是同一时刻，重新构建即可。
- **打个比方**：`docker cp` 像在租来的房子里贴便利贴，退租（重建容器）就没了；镜像是装修好的样板间，每次租房都按样板间交付。工作树是设计图，`build-image.sh` 是「按图重新装修」的那一步，不能省。

# 学习12：对外咨询页面的欢迎语来自页面 `subtitle`，不是机器人后台字段（2026-11-03）

- 关联：[对外咨询页面访问指南](../对外咨询页面访问指南.md) 第 3、8 节、`web/public/chat-jishi.html:32`、`web/public/chat-shell.js:102`、`src/langbot/templates/embed/widget.js:32`、`src/langbot/templates/embed/widget.js:1659`

疑问：

「没有预设提问时的欢迎语是怎么设置的？比如【你好，请问想了解什么？学院是国家重点技师学院，开设中级技工、高级技工和预备技师等培养层次，可咨询招生报名、专业设置、就业实习、校园生活和教学管理等公开事项。】」

解答：

- **结论先说**：这句话**不在机器人后台**，而是写死在独立聊天页自己的内联 JSON 里，字段名 `subtitle`。技师院页面就是 `web/public/chat-jishi.html:32` 的 `"subtitle": "你好，请问想了解什么？学院是国家重点技师学院……"`；学院公共页面在 `chat.html:24`，通用测试页在 `default.html:29`。
- **机制一（页面把配置塞给挂件）**：`chat-shell.js:102` 执行 `setAttr(script, 'data-subtitle', config.subtitle)`，把页面配置写成挂件脚本的 `data-subtitle` 属性。配置合并顺序仍是「内联 JSON → `?config=` 远程 JSON → `?embed=`/`?title=`/`?theme=`」，但 URL 参数里**没有** `subtitle`，所以换标题、换机器人、换主题色都不会改这句话。
- **机制二（挂件只认两个来源）**：`widget.js:32` 读取 `data-subtitle`，`widget.js:1659` 用 `scriptSubtitle || t("welcomeMessage")` 渲染欢迎区。也就是说：页面给了 `subtitle` 就显示页面这句；没给才退回挂件内置的多语言文案「发送消息开始对话」（`t()` 的语种来自机器人配置的 `language`，由 `embed.py` 注入为 `__LANGBOT_LOCALE__`）。机器人后台的适配器配置里**没有**欢迎语字段。
- **机制三（欢迎语和有没有预设提问无关）**：欢迎区固定渲染「Logo + `subtitle` + 分类 Tab」。有没有快捷提问只影响 Tab 出不出现；`subtitle` 一直都在。所以在没有预设提问时看到的那句话，仍然来自同一个 `subtitle` 字段，不是另一套“无提问专用文案”。
- **怎么改**：① 改页面文件 → `pnpm build` → 把新的 `chat-jishi.html` 同步到容器 `/app/web/dist/`（静态页是 `no-cache`，刷新即生效，不用重启）；② 不想动页面文件，就放一份只含 `"subtitle": "..."` 的远程 JSON，用 `?config=<地址>` 覆盖；③ 第三方网站直接嵌 `widget.js` 的，官方代码只生成 `data-title`，需要手动在 `<script>` 上加 `data-subtitle="..."`，挂件会读取它。
- **容易误判的点**：① 去机器人后台找「欢迎语」——那里只有标题、Logo、快捷提问分类等，没有这个字段；② 以为清空快捷提问会让欢迎语消失——清空只让 Tab 消失；③ 以为 `?embed=<另一个机器人>` 会换欢迎语——它只换“谁来回答”，页面品牌（含 `subtitle`）仍来自当前页面内联配置；④ 以为改了要重启 LangBot——静态页不走服务端进程，也不吃 `widget.js` 的 5 分钟缓存。
- **打个比方**：机器人是“店里的店员”，页面内联配置是“门口那块招牌”。招牌上写什么欢迎词由店面决定，换个店员（`?embed=`）不会自动改招牌；店员自己的默认招呼只有招牌空着时才顶上。

**更新（2026-11-03，新增后台「欢迎语」字段）**：

- **行为变了**：欢迎语不再只能写死在页面里。`web_page_bot.yaml` 新增 `welcome_message` 字段（类型 `text`，默认填一段通用欢迎语），后台「适配器配置 → 欢迎语」可直接编辑，不用改页面、不用重新构建前端。
- **优先级（高 → 低）**：测试页草稿 `#previewWelcome=...` → 机器人保存的 `welcome_message` → 独立页面 `subtitle` → 挂件多语言默认文案。实现位置：`embed.py` 把字段以 JSON 字符串注入 `__LANGBOT_WELCOME_MESSAGE__`（最后替换，防止文案里的 `__LANGBOT_*` 被再次改写），`widget.js` 的 `createWelcomeEl()` 按上述顺序取值。
- **为什么保留页面 `subtitle` 兜底**：已有机器人配置里没有这个新键，`embed.py` 注入空字符串，挂件自然退回页面品牌文案，升级不会让技师院/学院页面的欢迎语突然变成通用文案；管理员保存过「欢迎语」之后，字段才接管。
- **测试页草稿怎么传**：`DynamicFormComponent.openTestPage()` 把 `welcome_message` 编码成 `#previewWelcome=...`，`chat-shell.js` 读到后加 `data-preview-welcome="true"` / `data-welcome`；`widget.js` 看到标记就用草稿，**空草稿也会清空欢迎语**，与快捷提问草稿的行为一致。
- **边界**：保存为空 = 退回页面 `subtitle`（不是显示空白）；只有测试页的空草稿能制造“完全无欢迎语”的效果。改欢迎语走 `widget.js`，公开页最多约 5 分钟缓存；测试页带 `v=` 和草稿锚点，立即可见。

# 学习13：LangBot 的权限管「能做什么」，不管「谁能看到什么」（2026-11-03）

- 关联：`src/langbot/pkg/api/http/authz.py`、`src/langbot/pkg/workspace/policy.py`、`src/langbot/pkg/api/http/service/user.py:422`、`src/langbot/pkg/api/http/service/tenant.py:31`、`src/langbot/pkg/api/http/service/pipeline.py:111`

疑问：

「langbot 没有权限控制吗，为什么生产环境中账号 204618 和 admin@vocational.local 会看到相同的内容？」

解答：

- **结论**：LangBot 有 RBAC（基于角色的访问控制），但它控制的是「能不能改、能不能邀请、能不能管密钥」这类**动作**；pipeline、知识库、机器人、监控会话等**业务资源都挂在 Workspace 下**，同一 Workspace 的成员都能看到全部资源。OSS 自托管版本只允许一个 Workspace，所以两个账号看到同一份内容不是漏权限，而是「单工作区共享」的设计结果。
- **实测生产库**：`workspaces` 只有一条 `Default Workspace`（type=team、source=local）；`workspace_memberships` 里 `admin@vocational.local` 是 `owner`，`204618` 是 `operator`，两者的 `workspace_uuid` 相同。
- **机制一（角色→权限表）**：`authz.py:42` 的 `_ROLE_PERMISSIONS` 定义 owner/admin/developer/operator/viewer 五个角色。operator = `_VIEW_PERMISSIONS`（`workspace.view`、`member.view`、`resource.view`）+ `runtime.operate`，唯独没有 `resource.manage`。
- **机制二（资源按 Workspace 过滤，不按用户）**：`tenant.py:31` 的 `scope_statement()` 只加一个条件 `model.workspace_uuid == context.workspace_uuid`。pipeline 列表 `get_pipelines()`（`pipeline.py:111`）走这个函数，所以同一 Workspace 内所有人拿到的是同一份列表。
- **机制三（OSS 只有一个 Workspace）**：`policy.py:8` 的 `SingleWorkspacePolicy` 写明 `workspace_limit = 1`、`multi_workspace_enabled = False`；`entity/persistence/workspace.py:112` 的唯一索引 `uq_workspaces_local_instance` 又从数据库层保证每个实例只有一条 local Workspace。多 Workspace 属于 Cloud/SaaS 的 `CloudWorkspacePolicy`。
- **机制四（SSO 用户为什么是 operator）**：CAS 首次登录走 `establish_sso_account()` → `_ensure_sso_membership()`（`user.py:422`），新成员固定写 `role=operator`（`user.py:447`）；注释写明 operator 是「仍能使用聊天运行时」的最低角色。
- **两个账号的实际差异**：204618 能看全部 pipeline、知识库、机器人、监控会话，也能发起对话；但新建/编辑/删除按钮不显示（缺 `resource.manage`，`HomeSidebar.tsx:381`），`?id=new` 这类只写路由会被重定向（`layout.tsx:136`）；模型密钥（`provider_secret.manage`）、API Key（`api_key.manage`）、工作区语言设置（`workspace.update`）也都不可用。owner 则全部可用。
- **安全提醒**：生产配置 `sso.cas.auto_provision: true` 且 `allowed_user_types: teacher`，意味着**任何 CAS 里 usertype=teacher 的账号首次登录都会自动成为该 Workspace 的 operator**，能看到全部资源和监控数据。若这不是预期，应收紧 `allowed_user_types` 或关闭 `auto_provision`（关闭后只允许预先建好的账号登录）。
- **想按用户/部门隔离内容怎么办**：当前 OSS 构建做不到——RBAC 没有「按资源授权」，Workspace 上限又是 1。可行的是拆实例/独立部署；或者改代码引入多 Workspace 与资源级授权（属于架构改动，不是配置开关）。
- **打个比方**：Workspace 是一间大办公室，owner 是管理员，operator 是「只能看和用、不能搬家具」的访客。大家都进同一间办公室，自然看到同样的桌椅；权限决定的是能不能搬，不是能不能看。想让每个人进不同房间，得先有多个房间（多 Workspace）。
- **容易误判的点**：① 把「看到同样内容」当成越权，其实是同 Workspace 共享；② 以为 SSO 登录会创建个人独立空间，实际是加入唯一的工作区；③ 以为前端隐藏按钮就等于权限控制，后端的 `permission=` 才是权威边界（`layout.tsx:133` 的注释也说明了这一点）。

**2026-11-04 更新（代码已支持个人 Workspace，部署还没跟上）**：上面「OSS 只能有一个 Workspace」说的是当时运行的版本。仓库随后加入了 `PersonalWorkspacePolicy`（`src/langbot/pkg/workspace/policy.py`），每个账号一个 `personal-{account_uuid}` 空间；SSO 首次登录走 `ensure_personal_workspace()`，存量账号由 Alembic `0043_personal_workspaces` 在启动时迁移——Default 的 owner 留下，其余账号各建空空间并把旧共享成员关系置 `removed`。但**代码提交不等于线上生效**：生产镜像是 11-03 的 `191ab9a7`、本地镜像是 11-03 构建的 `ca469af9`，个人工作区提交 `3213d2ae` 是 11-04 08:11 才提交，两个镜像都不包含它，所以 204618 仍按旧逻辑看到全部内容。判断「某个功能到底上没上」要看 `langbot._build_info.CORE_REVISION` 与 `git merge-base --is-ancestor <功能提交> <镜像 revision>`，不要看仓库工作树或容器里有没有代码文件。[问题13](../问题记录/问题记录.md#问题13204618-登录-langbot-后仍能看到-admin-的机器人和知识库个人工作区只在代码里没进镜像2026-11-04)记录的就是这次误判。

# 学习14：模型的「能力」开关决定 MCP 工具会不会被挂上——没工具时模型会编数据（2026-11-03）

- 关联：[问题10](../问题记录/问题记录.md#问题10企微问数机器人回答2025-年各专业就业率排名时编造毕业生数就业人数)、`src/langbot/pkg/pipeline/preproc/preproc.py:278`、`web/src/app/home/components/models-dialog/components/ModelItem.tsx`

疑问：

「模型明明配了 MCP 数据源，为什么回答里的数字和源表对不上，还编得像模像样？」

解答：

- **结论**：MCP 服务器配好了不等于模型能用它。流水线在预处理阶段会检查模型记录里的 `abilities`（能力标签）数组，只有包含 `func_call`（函数调用）才会把工具挂给模型；数组为空时一个工具都不注入。
- **机制**：`preproc.py:278` 的条件是 `if uses_host_tools and 'func_call' in (llm_model.model_entity.abilities or [])`。`uses_host_tools` 只表示「这个 pipeline 想用宿主机工具」，真正的门禁是 `abilities`。三个能力标签分别是 `vision`（视觉）、`func_call`（函数调用）、`reasoning`（思考能力），在 WebUI「设置 → 模型」里就是三个勾选框。
- **编造是这么发生的**：模型拿不到工具，但对话历史里有上一次的答案，于是它直接复读旧数据，再按就业率反推人数——市场营销源表 130/128，回答写成 195/192（195 × 98.46% ≈ 192），数学上自洽，所以肉眼很难发现。
- **判别方法**：① 看 `monitoring_tool_calls` 有没有 `status=success` 的 `mcp_ask`；② 看 `agent_run_event` 是否只有 `message.delta`、没有 tool_call 事件；③ 回答耗时特别短、输出特别长，且 SQLBot 的 `chat_record` 没有对应记录，基本就是没查库。
- **容易误判的点**：① 以为「MCP 服务连上了」就代表模型能调；② 以为模型自己会判断该不该调工具——它压根不知道工具存在；③ 新建模型时忘了勾选能力，之后所有问答都静默降级，不报错。
- **修复后不用重启**：在 WebUI 保存模型会走 `update_llm_model`（`src/langbot/pkg/api/http/service/model.py:480`），依次 `remove_llm_model` → `load_llm_model_with_provider` → `cache_llm_model`，热重载立即生效。但**已经加载的会话历史还在内存里**，要让模型忘掉旧答案，需要用户发 `/reset` 或重启进程。

# 学习15：MCP 的 scoped token 把「工作区」写死在凭据里，工作区迁移后必须重新导出（2026-11-03）

- 关联：[问题11](../问题记录/问题记录.md#问题11修复工具注入后-mcp_ask-返回-403凭据校验失败sso-独立工作区迁移后旧-mcp-token-失效)、`apps/mcp/auth.py:111-176`（SQLBot 侧）、`apps/system/api/apikey.py`（`/mcp-config` 导出接口）

疑问：

「MCP 配置里明明有 token，为什么调用时报 403 Could not validate credentials？」

解答：

- **结论**：SQLBot 导出的 MCP 配置不是普通 API Key，而是一枚 **scoped JWT**（作用域令牌）——token 里直接写着 `uid`（用户）、`oid`（工作区）、`datasource_id`（数据源）、`access_key`（对应哪个 API key）。任何一项在服务端对不上就 403，而且**工具列表能正常拉取、只有真正调用时才失败**，很容易误判成数据源坏了。
- **机制**：`_resolve_scoped_principal`（`apps/mcp/auth.py:111`）依次校验：token 的 `scope` 是否为 `mcp`、`access_key` 对应的 key 是否存在且启用、用该 key 的 `secret_key` 验签、`uid` 是否等于 key 的持有者、用户是否属于 `oid` 工作区、数据源是否也属于 `oid`。全部通过才放行。
- **本次为什么失效**：10-30 签发的 token 写的是 `oid=1`；11-03 SSO 独立工作区迁移后，`admin@vocational.local` 只属于工作区 3，数据源 `id=2` 也改归 `oid=3`，旧 token 永远对不上——不是 token 被篡改，而是它描述的「世界」已经变了。
- **正确做法**：重新走 SQLBot 的导出接口 `GET /api/v1/apikey/{id}/mcp-config?datasource_id=2`，它按数据源**当前所属工作区**重新签发；手工用同一 `secret_key` 签一个 `oid=3` 的 token 效果等价。
- **替换后怎么生效**：LangBot 的 `update_mcp_server`（`src/langbot/pkg/api/http/service/mcp.py:446`）会删除旧会话并重新 `host`，保存即热重载，不用重启容器。
- **容易误判的点**：① 「MCP 工具列表能拉到」不等于「能调用」，鉴权发生在工具调用内部；② 把 403 当成网络/数据源问题，实际是凭据里的工作区过期；③ 工作区迁移只迁移了数据，忘了迁移各集成里已经签发的凭据。

# 学习16：嵌入的 SqlBot 是独立 SPA，401 默认只会回自己的登录页（2026-11-03）

- 关联：[问题12](../问题记录/问题记录.md#问题12sqlbot-接口失效后落到-sqlbot-登录页而不是-langbot-统一退出)、`SQLBot/frontend/src/utils/request.ts`、`SQLBot/frontend/src/router/watch.ts`、`SQLBot/frontend/src/utils/portal.ts`、`web/src/app/login/page.tsx:133`

疑问：

「SqlBot 应用还有很多接口失效后，退出的界面是 SqlBot 的界面，而不是统一登出的 LangBot 界面。为什么网关已经把两个应用放在同一个域名下，还是会各退各的？」

解答：

- **结论**：同一个域名不等于同一套会话。SqlBot 是独立打包的 SPA，有自己的 token（`user.token`，实际存储键带 `sqlbot_` 前缀）和自己的登录页；它的 401 处理只认自己的状态，不会主动去问 LangBot。LangBot 的统一退出入口 `/login?logout=1` 虽然存在，但 SQLBot 之前没有调用它。
- **机制一（axios 401）**：SqlBot 的 axios 响应拦截器在 `request.ts` 的 `handleError()` 里处理 401：普通会话先 `ElMessage` 提示，2 秒后删 `user.token` 并 `window.location.reload()`；重载后 `router/watch.ts` 发现没有 token，就 `next(toLoginPage(...))` 跳到 SQLBot 的 `#/login`。assistant 会话则直接进 `/401` 页面。两条路都止步于 SqlBot 自己的界面。
- **机制二（流式接口绕过拦截器）**：聊天、分析、预测等接口调用 `fetchStream()`，它用原生 `fetch` 而不是 axios，因此不会触发上面的拦截器；401 只会让流提前结束，页面看起来“没反应”，直到下一次普通请求 401 才跳登录页。
- **机制三（门户标记只是标记）**：从应用中心进入时，SQLBot 在票据兑换成功后写 `sqlbot_portal_session=1`（`utils/portal.ts` 的 `markPortalSession()`）。它只说明「这次会话是 LangBot 开的」，本身没有跳转能力；401 处理必须先读这个标记，才知道该回 LangBot 而不是本地登录页。
- **为什么不在 nginx 上拦 401**：网关只做路径分流，401 是 SPA 内部的 API 响应；如果在网关层把 401 统统重定向到 `/login`，登录接口本身的 401（密码错误、票据过期）也会被改写，反而破坏登录流程。正确的边界是前端按「这是不是一个门户会话」决定去哪。
- **统一的落点**：LangBot 的 `/login?logout=1` 是一个强制清理入口（`web/src/app/login/page.tsx:133`），会调用 `clearLocalSession()` 删掉 LangBot token、`userEmail` 和所有 `sqlbot_` 前缀键，再显示 LangBot 登录页。所以 SQLBot 检测到门户会话 401 时，跳这里就能一次清干净两边。
- **本次修复的四个入口**：axios 401、`fetchStream` 401、路由守卫无 token、`/401` 页挂载；共同调用 `utils/portal.ts` 新增的 `redirectToLangbotLogout()`。显式点「返回应用中心」仍只结束 SqlBot 会话、回 `/portal`，不强制登出 LangBot。
- **打个比方**：LangBot 和 SqlBot 像同一栋楼里的两家店，门牌号都在 `/` 下，但各有各的门禁卡。SqlBot 的卡刷不开时，店员默认把你带到自家服务台；除非提前告诉店员「你是从一楼大厅前台领的访客卡，出问题请把我送回前台」，否则不会自动去 LangBot 的出口。
- **判别方法（30 秒版）**：在 SqlBot 页面打开 DevTools → Application → Local Storage，看有没有 `sqlbot_portal_session=1`；有 = 门户会话，401 应去 LangBot `/login?logout=1`；没有 = 本地密码会话，401 回 SQLBot 登录页是预期行为。
- **容易误判的点**：① 以为同源/同域名就共享登录态——实际只有 cookie 共享，localStorage 各用各的前缀；② 把 403 也当成登录失效——403 是权限不足，不应触发登出；③ 只改了 axios 拦截器就以为覆盖全部接口——流式 `fetch` 和路由守卫是另外两条入口；④ 以为 LangBot 会话一定也失效了——SqlBot token 先过期时 LangBot 可能仍然有效，本次按用户确认选择了「统一登出」，所以两边都会清。

# 学习17：在 Docker 容器里跑 nsjail，需要同时满足权限、cgroup 和目录属主三个条件（2026-11-04）

- 关联：[问题15](../问题记录/问题记录.md#问题15生产升级后三个插件全部不可用nsjail-在容器里的权限cgroup-和目录属主都不满足2026-11-04)、`langbot_plugin/runtime/plugin/worker_launcher.py`、`deploy/prod/docker-compose.yaml`

**一句话**：nsjail 不是「装进镜像就能跑」的普通程序，它要在容器里再建一层 user/mount/pid/cgroup 命名空间；Docker 默认的权限模型会把这些能力一层层关掉，而它挂载的目录还必须能被新命名空间里的 uid 0 访问。

三个条件（缺任一都会让 nsjail 以退出码 255 结束，插件随之反复重启）：

1. **命名空间权限**：seccomp 默认拦截带 `CLONE_NEWUSER` 的 `clone`，即使 `cap_add: SYS_ADMIN` 也可能因 Docker 的 masked paths 挂不了 `/proc`。需要 `SYS_ADMIN` + `seccomp=unconfined` + `apparmor=unconfined` + `systempaths=unconfined`。
2. **cgroup v2 控制权**：nsjail 用 cgroup 限制内存/PID/CPU，但 Docker 默认的私有 cgroup 命名空间里写不了 `cgroup.subtree_control`；需要 `cgroup: host`（CLI 是 `--cgroupns=host`），并且把宿主 `/sys/fs/cgroup` 以可写方式再挂进容器，否则 `mkdir NSJAIL.<pid>` 会报只读。
3. **被挂载目录的属主**：nsjail 在 user namespace 里是「映射后的 root」。如果 chroot 根目录是旧容器以 uid 1001 创建、权限 0700，新命名空间的 uid 0 既不是 owner 也没有对应 `CAP_FOWNER`，连 `chmod o+x` 都失败，报 `try 'chmod o+x' on source path: Permission denied`。把数据目录 `chown 0:0` 并放开 `a+rX` 即可。

**打个比方**：nsjail 像在小区里给自己搭一间独立的工具房。条件 1 是「物业允许你动土」；条件 2 是「物业把水电总闸给你接出来，而且不是关着的」；条件 3 是「工具房的门锁不能挂在上一任租户名下」。三者少一个，工人都进不了门，但整栋楼（LangBot 主进程）看起来仍然一切正常。

**判别方法（30 秒版）**：

```bash
# 条件 1：直接跑 nsjail，看 clone(...) Operation not permitted
sudo docker exec <runtime> nsjail --mode o --chroot / -- /bin/true
# 条件 2：加 --use_cgroupv2，看 Couldn't setup parent cgroup 或 Read-only file system
sudo docker exec <runtime> nsjail --mode o --chroot / --use_cgroupv2 \
  --cgroup_mem_max 1073741824 --cgroup_pids_max 256 --cgroup_cpu_ms_per_sec 1000 -- /bin/true
# 条件 3：看安装目录属主，不是 0:0 且不是 0755 就可疑
sudo docker exec <runtime> stat -c '%a %u:%g %n' /app/data/plugin-runtime/installations/*/root
```

**容易误判的点**：① 只看容器 `healthy` 就以为插件正常——worker 是在容器里再起的子进程，容器健康检查覆盖不到；② 用 `nsjail --help` 能执行就以为 nsjail 可用——`--help` 不创建命名空间；③ 以为 255 一定是 pip 网络错误——255 也是 nsjail 自身启动失败的退出码，SDK 丢弃了它的 stderr，需临时把 `--really_quiet` 换成 `-v` 或直接复现参数才能看到真实原因；④ 以 root 身份能写目录就以为 nsjail 也能写——它用的是新 user namespace 里的 root，权限检查针对的是映射关系和 inode 属主，不是容器外看到的 uid。

# 学习18：聊天页闲置久了发送按钮变灰，不是样式问题，是 WebSocket 重连预算用完了（2026-11-05）

- 关联：[问题16：对话页闲置较久后发送按钮变灰、点不动](../问题记录/问题记录.md#问题16对话页闲置较久后发送按钮变灰点不动embed-widget-的-websocket-重连-5-次后永久放弃2026-11-05)；代码 `src/langbot/templates/embed/widget.js`

疑问：

`chat.html` 和 `chat-jishi.html` 很久不访问后，点发送按钮是灰的、点不动，是什么原因？

解答：

- 先看现象归属：那条灰色按钮是输入框右侧的发送按钮，禁用条件写死在 `updateSendBtn()`：`sendBtn.disabled = !state.isConnected`（修复前 `widget.js:1731`，现 `:2032`）。也就是说「按钮灰」等价于「前端认为自己没连上 WebSocket」，不是主题色或权限问题。
- 重连预算（修复前行为）：`onclose`（旧版 `widget.js:882`）最多重试 5 次，间隔是 3 秒乘以第几次，即 3、6、9、12、15 秒，总共约 45 秒。第 5 次之后不再安排任何重试——`maxReconnectAttempts: 5` 在旧版 `widget.js:227`。
- 最容易误判的点（修复前行为）：`onopen` 成功时会把 `reconnectAttempts` 清零（旧版 `widget.js:863`）。所以「WS 能打开、但马上被服务端断开」会无限重试（实测每 4.5 秒一次）；真正把预算用光的是**连接根本打不开**——服务端停止、电脑睡眠后网络未就绪、`baseUrl` 指到不可达地址。这两类断开看起来都是「按钮灰」，但前者会自愈，后者不会。
- 为什么不自动恢复（修复前）：`wsConnect()` 只在页面自动打开和手动展开面板时调用（旧版 `widget.js:1737`），没有监听 `online` / `focus` / `visibilitychange`。同仓库 WebUI 的 `WebSocketClient` 有这三个恢复事件（`web/src/app/infra/websocket/WebSocketClient.ts:45`、`:121`），embed widget 没同步。这也解释了为什么「收起再展开聊天气泡」「刷新页面」能立刻恢复——这两个动作都会重新调用 `wsConnect()`。
- 浏览器侧放大因素：后台标签页的定时器会被节流，电脑睡眠会冻结定时器；醒来后如果网络还没就绪，5 次退避很快用完，等服务恢复时页面已经放弃。
- 判别方法：DevTools → Network → WS，观察是否还有新的 `ws/connect`（101）请求。断网超过 45 秒后恢复，若不再出现新请求且按钮保持灰，就是预算耗尽；能在 Network 里看到 `ws/connect` 反复出现（101 后立即关闭），则更像服务端拒绝或认证失败，而不是预算问题。

延伸：

- 已按「补恢复事件监听 + 有上限间隔的无限重试」修复（2026-11-05）：退避 3s 起、封顶 30s 并带抖动；只在服务端 `connected` 认证成功后清零；新增心跳判活与可见状态横幅。实现位置与验证记录见[问题16 的实际处理方案](../问题记录/问题记录.md#问题16对话页闲置较久后发送按钮变灰点不动embed-widget-的-websocket-重连-5-次后永久放弃2026-11-05)。
- **通用记忆点**：凡是自建 WebSocket 客户端，「重试次数有上限」几乎总是隐患；正确组合是「无限退避 + online/visibility 恢复事件 + 心跳判活」。另外 `onopen` 只代表 TCP/握手成功，不代表业务可用，退避计数应在业务握手成功后重置。
- 另一个会让按钮「一打开就灰」的原因是 `api.webhook_prefix` 配成 `127.0.0.1`，LAN 浏览器会连自己的 localhost；排查时先确认 `curl .../widget.js | grep baseUrl` 返回的是浏览器实际可达的地址。
